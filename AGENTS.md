# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project

TV Bro is an Android web browser for TV remotes (D-pad navigation, virtual cursor, tabs, bookmarks, voice search, downloads, history), with a touch interface for phones in the same APK. It can render pages with either the system WebView or a bundled GeckoView engine. Package/applicationId: `com.phlox.tvwebbrowser`.

## Build & test

Gradle (Kotlin DSL) with JDK 21. On Windows use `gradlew.bat` / `.\gradlew`.

Variants combine two flavor dimensions with the build type: `appstore` = `generic` | `google` | `foss`, and `webengine` = `geckoIncluded` | `geckoExcluded`. Examples:

```bash
./gradlew assembleGenericGeckoIncludedDebug
```
```bash
./gradlew assembleGenericGeckoExcludedRelease
```
```bash
./gradlew testGenericGeckoIncludedDebugUnitTest
```
```bash
./gradlew :app:testGenericGeckoIncludedDebugUnitTest --tests "com.phlox.tvwebbrowser.utils.FaviconExtractorTest"
```
```bash
./gradlew :app:common:testDebugUnitTest
```

- Pass `-PenableAbiSplits` to `assemble` to produce per-ABI APKs (armeabi-v7a, arm64-v8a, x86_64).
- Release signing reads the env vars `KEYSTORE_PATH`, `KEYSTORE_PASSWORD`, `KEY_ALIAS` and `KEY_PASSWORD`. Without `KEYSTORE_PATH`, release builds are unsigned.
- App unit tests use Robolectric (`isIncludeAndroidResources = true`). There are no instrumented tests. Browser core tests use `FakeWebEngine` (registered through `WebEngineFactory.initializeForTests`) and an in-memory Room database (`AppDatabase.setInstanceForTests`).
- Room schemas are exported to `app/schemas` and committed. `AppDatabaseMigrationTest` builds databases of old versions from them, so a database version bump needs its schema exported (it is generated by the build) and a migration test.
- `buildSrc` compiles with `allWarningsAsErrors = true`.

## Module layout

- `:app`: the base application. It holds the browser core (`browser` package, see below), the UI (activities, dialogs, settings), the Room `AppDatabase`, the download service, the WebView engine (`webengine/webview`), adblock and auto-update.
- `:app:common`: an Android library shared by `:app` and `:app:gecko`. It holds the engine abstraction (`webengine/WebEngine.kt` and `WebEngineFactory`), the `Config` prefs, the Room entity models, `AppContext`, `ActiveModel`/`ActiveModelsRepository`, and the cursor widgets (`CursorLayout`, `CursorDrawerDelegate`). Code that both engines need belongs here, because the gecko module must not depend on app-only classes.
- `:app:gecko`: the GeckoView engine (`GeckoWebEngine`, delegates, and a bundled WebExtension under `assets/extensions/generic`). An Android library that `:app` depends on only in `geckoIncluded` variants (`geckoIncludedImplementation`); its keep rules for the app's R8 are in `consumer-rules.pro`.
- `buildSrc`: convention plugins `tvbro.android.application` and `tvbro.android.library` (both in `TvBroAndroidModulePlugin.kt`). They apply AGP and set compileSdk, minSdk and targetSdk from `gradle/libs.versions.toml`. The product flavors are declared in `app/build.gradle.kts`. All dependency versions live in that version catalog.

## Key architecture

**Web engine plug-in mechanism.** Engines register themselves rather than being referenced directly. Each engine class has a `companion object { init { WebEngineFactory.registerProvider(...) } }`. `TVBro.initWebEngineStuff()` triggers that registration through reflection (`Class.forName("...WebViewWebEngine")` and `Class.forName("...GeckoWebEngine")`). A `ClassNotFoundException` for Gecko is expected in variants that leave it out. `WebEngineFactory.initialize()`, called from `MainActivity`, picks the provider whose name matches `Config.webEngine` and falls back to the first registered one. Settings only shows the engine picker when more than one provider is registered. **Keep base-app code free of compile-time references to gecko classes.** All interaction goes through the `WebEngine` interface and `WebEngineFactory`. Common code must not check which engine is active either: engine-specific behavior goes through `WebEngineProviderCallback` hooks (incognito data isolation and cleanup, failure to create a view, `supportsSetting` for settings only some engines have, see `EngineSpecificSetting`) or `WebEngine` properties (for example `stateFilePrefix` of saved tab state files). `BrowserTab.webEngine` is created lazily; check `isWebEngineCreated` before touching the engines of all tabs.

**Virtual cursor.** The cursor is an optional engine capability: an engine that supports it implements `VirtualCursorSupport` (cursor vs. direct navigation mode, the `CursorDrawerDelegate`), and the UI reaches it only through `webEngine.virtualCursor`. Each engine owns its cursor surface: the WebView engine wraps every `WebViewEx` (and its fullscreen view) in its own `CursorLayout`, Gecko draws the cursor on `GeckoViewWithVirtualCursor` (one view shared by all tabs). The activity's tabs container (`flWebViewContainer`) is a plain `FrameLayout`. When another tab is shown, `MainActivity.onRenderedTabChanged` turns the grab and direct navigation modes off.

**Shells: the TV and the phone UI.** `MainActivity` does what both looks share (the browser core, intents, navigation, incognito, downloads, keys and Back) and leaves the look to a `BrowserShell`, which it creates in `onCreate`: `TvShell` (`activity_main.xml`: the bar of the redesign over the page, the virtual cursor) or `PhoneShell` (`activity_main_phone.xml`: touch only, the virtual cursor is turned off for every tab view, the bottom `PhoneBar`, which `ScrollAwayBar` slides away while the user scrolls the page down (touches are tracked by the tabs container, `TouchTrackingFrameLayout`), the `PhoneMenuSheet`, the `PhoneTabSwitcher` and the `PhoneBookmarksView` over the window). The shell gets the activity as `BrowserShell.Host` and is told about the engine views, the current tab state, UI events, fullscreen and Back. `UiModeSelector` picks the shell from the Interface setting (`Config.interfaceMode`); on Auto, the phone UI is for devices that are not a TV, have no leanback feature, have a finger touch screen and are narrower than 600dp (no tablets for now). Changing the setting restarts the app. The activity is not recreated on rotation or size changes (`configChanges`), so the engine views stay; the phone window is drawn edge to edge and `PhoneShell` applies the insets. Settings (`SettingsDialog(touchUi = true)`) leave out the shortcuts and the cursor settings on the phone. The built-in home page has a layout for phones (a CSS media query in `assets/pages/home/index.html`; the copy on the website, used by GeckoView, has to be kept the same).

**Commands and Back.** Browser actions triggered by the user from anywhere (hotkeys of `ShortcutMgr`, voice search) go through `browser/BrowserCommands`, which the activity implements; the buttons of the TV bar call `BrowserController` from the shell. Every Back (the BACK/ESCAPE key, the system back callback, the B button of game controllers) goes through `BackNavigationEventsAdapter`: it removes duplicates between these channels and handles the "long press B" mode of game controllers in the direct navigation mode. The adapter feeds `MainActivity.screenBackDispatcher`, an own `OnBackPressedDispatcher` of the screen: each overlay has an `OnBackPressedCallback` there that it enables while it is shown, registered in `onCreate` from the lowest priority (the menu) to the highest (the cursor modes, which come from `VirtualCursorSupport.cursorModes`). Never add overlay callbacks to the activity's `onBackPressedDispatcher`: it has one always enabled callback that goes to the adapter. When something else has already handled a Back press in progress (the fullscreen view of WebView leaves fullscreen on BACK down), call `consumeCurrentPress()`.

**Browser core and engine callbacks.** `browser/BrowserController` (an `ActiveModel`) owns the tabs: their list, the current tab, persistence, opening/closing/switching, navigation, the engine events and the browsing history. It knows nothing about views: an activity attaches itself as `BrowserController.TabViewHost`, which creates engine views (`createTabView`) and provides the UI part of the engine callbacks (`uiHost`). The engine of the current tab gets a `WebEngineCallbacks` in `onAttachToWindow`; it is composed of three parts, all in `webengine/WebEngineCallbacks.kt`: `TabEngineEvents` (implemented by the controller), `EnginePolicies` (`TabPolicies`: ads, dialogs and new windows blocking) and `EngineUiHost` (implemented by the activity: menus, dialogs, fullscreen, page scrolling, permissions and file picking with result callbacks, downloads as `DownloadRequest`). The callbacks are set only while the tab is current, so background tabs report nothing. The UI renders `BrowserController.currentTabState` (`StateFlow<CurrentTabState>`) and handles one-time `BrowserUiEvent`s from `uiEvents` (a channel with a single collector). Other core pieces: `HomePageLinks` (links of the built-in home page), `VisitedHistoryLogger`, `HomePageUrl` (resolves `about:home`, engines never get the alias), `UrlRouter`/`UrlInputResolver`/`PopupBlockPolicy`, `Downloads.kt`. Activities start other activities and ask for permissions through `utils/launchForResult` (the ActivityResult registry), never with request codes; `activity/main/DownloadLauncher` starts downloads.

**State models.** Screens keep state in `ActiveModel` subclasses (for example `BrowserController`, `SettingsModel`, `AdblockModel` and `ActiveDownloadsModel`). They get them through `ActiveModelsRepository.get(Model::class, activity)`, not through AndroidX ViewModel. A model is released when every activity using it finishes. Older observable state uses the custom `utils/observable` types (`ObservableValue` and `ObservableList`); new code uses `StateFlow`/`Flow` (with immutable values: a `StateFlow` does not emit a value equal to the previous one).

**Tabs.** `BrowserTab` (in `:app:common`, engines get it) is a tab in memory: its engine, thumbnail and page state; it is read and changed on the main thread only. The database keeps `TabEntity` snapshots (`toEntity()`/`fromEntity()`), and `browser/TabFilesStore` keeps the files of tabs (engine states, WebP thumbnails), getting and returning file names without touching tabs. `BrowserController.saveTab` takes the snapshot when called and enqueues the write in `tabWrites`; the queue runs on the main thread, so the id and the file names given by earlier writes are applied there. A tab is saved when it stops or starts being the current one and when the activity pauses.

**Bookmarks.** `FavoriteItem`s are kept in folders: a folder is an item without a url, its contents point to it with `parent` (0 is the top level, `FavoritesRepository.ROOT`). The bookmarks of the built-in home page are the Home page folder (`FavoritesRepository.HOME_PAGE`, no row in the table: they are marked with `homePageBookmark`, hold no folders and are not in the top level). In a folder, folders come first, then bookmarks, each by `order` (the newest first among equal orders): new items go to the top, new home page bookmarks to the end. The home page shows the bookmarks of its folder in that order (a link's `order` is its place on the page) and leaves out those it has no room for; `HomePageLinks.load()` is called after bookmarks change. Use the repository (`add`, `moveTo`, `move`, `delete` with the contents of a folder), not the DAO. What the bookmarks screens show and do is in `BookmarksNavigator` (no views: a stack of screens, a folder, the form of a bookmark or folder, the choice of a folder, rendered through its `Host`); the shells only draw it. The TV shell shows it in `BookmarksPanelView`, under the star of the bar, with the row menus in a `PopupMenuView` (both are `AnchoredOverlayView`s, which keep the focus inside them while open). The phone shell shows it in `PhoneBookmarksView` over the whole window, with the actions of a row in a `PhoneActionsSheet` and reordering by dragging; the Bookmark button of the menu sheet adds the page, or opens its bookmark.

**Global singletons.** `AppContext.get()` and `AppContext.provideConfig()` (initialized in `TVBro.onCreate`) give `:app:common` code access to the Application and the `Config` SharedPreferences wrapper. The Room database (`AppDatabase`, its schema version and hand-written migrations are in `singleton/AppDatabase.kt`) is opened by `AppContainer.database`; the app and the UI reach the data only through the repositories of `AppContainer.data` (`data` package: tabs, history, favorites, downloads, host configs), never through DAOs. `TVBro.container` (`AppContainer`; code that only needs a `Context` uses `AppContext.get()`, not the `TVBro` instance) also holds the application-wide `appScope` and `tabWrites`, a `SerialWriteQueue` through which all tab database and file writes go: they run one by one and are not cancelled with the activity or the model. Code that exits the process (`exitProcess`) waits for `tabWrites.awaitPending()` first, asynchronously; to exit (and optionally restart) when `MainActivity` finishes, call `TVBro.exitProcessAfterMainActivityFinish`.

**Flavors.** `BUILT_IN_AUTO_UPDATE` (a BuildConfig field) is true only for `generic`. The auto-updater reads `latest_version.json` from the repo (release/beta channels with per-ABI APK URLs). `foss` adds the `.foss` applicationId suffix. `geckoIncluded` raises minSdk to 26 and adds the gecko module.

**Home page.** `about:home` (`Config.HOME_URL_ALIAS`) is resolved by `HomePageUrl` in the core according to the home page mode; the built-in home page is `Config.HOME_PAGE_URL`. The page itself is in `app/src/main/assets/pages/home` (`index.html` and `index.js`, no inline scripts or handlers), and both engines show it from the APK: WebView serves it in `shouldInterceptRequest` under `Config.HOME_PAGE_URL`. GeckoView cannot serve local files that way, so the build of the gecko module copies the page into the bundled extension (`assets/extensions/generic/home`, a generated assets directory) and GeckoView shows it as a page of the extension (`moz-extension://…/home/index.html`). `GeckoWebEngine` hides that: it loads the local page for `Config.HOME_PAGE_URL` (waiting for the extension at startup), reports it back as `Config.HOME_PAGE_URL`, and replaces the web version (old links, saved tabs) with it. The page talks to the app through the `TVBro` object: added by WebView's `AndroidJSInterface`, or defined by `index.js` over the extension port (`AppHomePagePortDelegate`; the app calls the page through the port too, since extension pages run no `javascript:` urls). The extension is installed again when the hash of its files (`BuildConfig.WEB_EXTENSION_HASH` of the gecko module) changes. The web copy at tvbro.phlox.dev (the `tv-bro-web` repository) is only for older versions of the app.

**Look.** Colors come from theme tokens: `?attr/tbColor…` attributes (`values/attrs.xml`) that `Theme.TVBro` maps to the semantic palette in `values/colors.xml` (night values in `values-night`). Layouts and drawables use the attributes, never hex colors or palette colors directly; code uses `Context.themeColor(R.attr…)`. Attributes need a themed (activity) context: do not inflate such views or drawables with the application context. A theme attribute does not resolve in `android:drawable` of a selector item (the drawable fails to load): put the color in a `<color>` or `<shape>` element inside the item. `ThemeResourcesTest` loads every drawable and color of the app with the app theme. The redesigned screens (the TV bar, the phone UI) use the tokens of the "TV Bro" design system instead: `?attr/tbColorDs…` attributes named as in its `tokens.json` (mapped to `ds_…` palette colors, night values in `values-night`), `ds_…` dimens, the `Widget.TVBro.Text.Address`/`Toast`/`MenuItem`/`TabTitle`/`CountBadge` styles and the `ds_…` state drawables (focused also when hovered by the cursor, selected when activated or selected). The other screens keep the older `tbColor…` palette until they are redesigned. Widgets get their look from styles in `values/styles.xml`, set with `style="..."` on each view: `Widget.TVBro.Button`/`Widget.TVBro.ImageButton` (the app button background; `.CursorMenu` adds the tint of the cursor menu; `.Ds.Segment`, `.Ds.Standalone` and `.Ds.Field` are the buttons of the redesigned bar) and `Widget.TVBro.Text.*` for text sizes (`Headline`, `Title`, `Subtitle`, `Body`, `Caption`, `Badge`; sizes in `values/dimens.xml`). These text styles set only `textSize`: a `textAppearance` would replace the default text color of the view. The theme sets no widget defaults (`buttonStyle` and others), so a view without a style keeps the platform look. Repeated spacing values are dimens (`settings_content_padding`, `settings_section_spacing`, `list_item_padding_*`). Icons are one vector per glyph with a role name (`ic_back`, `ic_close`, `ic_favorites`…): white paths and `android:tint="@color/icon_tint"`, which gives the icon color and the disabled one for a disabled view, so there are no per-color copies or selectors swapping images. A view that needs another color sets `app:tint` with a token (the cursor menu, `tbColorIconSubtle` for the bookmark edit and delete buttons). An icon needed at another size in a `wrap_content` button gets a `layer-list` wrapper with the size, not a fixed view size: the button is then rounded to pixels like other icons of that size.

**Lists.** Lists are `RecyclerView`s with focusable rows (`Widget.TVBro.ListItem`: focusable, `list_item_bg_selector` background); there is no `ListView` left. History and downloads are lists grouped by days (`widgets/datedlist`): `DatedListAdapter` (a `ListAdapter` that builds the header rows from the items, diffed in the background; act on the new rows in the `submitItems` callback), `StickyHeaderDecoration` (the pinned header of the top day with its shadow), `ListDividerDecoration`, and `StickyHeaderLayoutManager` (scrolls a focused row out from under the pinned header). They are in a `NearestFocusRecyclerView`: focus coming into the list from another view (`nextFocus...` set to the list) goes to the row nearest to that view, as in a ListView, and a focus request made while the layout is pending keeps the row that got it.

## Release

Releases use the manual `.github/workflows/release.yml` workflow (`workflow_dispatch` with a version). It builds per-ABI `genericGeckoIncluded` APKs (`-PenableAbiSplits`) and the `genericGeckoExcluded` release APK, renames them `tvbro-<version>-...apk`, and publishes a GitHub release whose body is `RELEASE_NOTES.md`. A version bump touches `versionCode`/`versionName` in `app/build.gradle.kts`, `latest_version.json`, `RELEASE_NOTES.md`, and the F-Droid/Play metadata changelog under `metadata/en-US/changelogs/<versionCode>.txt`. The app reads `latest_version.json` from `master` on GitHub, so changes to it go live once merged.
