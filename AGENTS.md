# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project

TV Bro is an Android web browser for TV remotes (D-pad navigation, virtual cursor, tabs, bookmarks, voice search, downloads, history), with a touch interface for phones in the same APK. It is built as two separate apps that differ in the engine rendering pages: the system WebView (applicationId `com.phlox.tvwebbrowser`) or a bundled GeckoView (`com.phlox.tvwebbrowser.gecko`). The engine of an app can not be changed.

## Build & test

Gradle (Kotlin DSL) with JDK 21. On Windows use `gradlew.bat` / `.\gradlew`.

Variants combine two flavor dimensions with the build type: `appstore` = `generic` | `google` | `foss`, and `webengine` = `geckoIncluded` (the GeckoView app) | `geckoExcluded` (the WebView app). Examples:

```bash
./gradlew assembleGenericGeckoIncludedDebug
```
```bash
./gradlew assembleGenericGeckoExcludedRelease
```
```bash
./gradlew testGenericGeckoIncludedDebugUnitTest
```
```bash
./gradlew :app:testGenericGeckoIncludedDebugUnitTest --tests "com.phlox.tvwebbrowser.utils.FaviconExtractorTest"
```
```bash
./gradlew :app:common:testDebugUnitTest
```

- Pass `-PenableAbiSplits` to `assemble` to produce per-ABI APKs (armeabi-v7a, arm64-v8a, x86_64).
- Qwant is a partner search engine: its partner ID (the `client` parameter of its searches and of its home page) is kept out of the repository, so forks do not send it. The build reads it from the Gradle property `qwantClientId` (`~/.gradle/gradle.properties` for local and Google Play builds) or the env var `QWANT_CLIENT_ID` (the secret of the release workflow, which fails without it) into `BuildConfig.QWANT_CLIENT_ID` of `:app:common` (`Config.QWANT_CLIENT_ID`, `QWANT_PARTNER`). Without it Qwant is listed without the parameter and Google stays the default. With it, `DefaultSearchEngine.applyOnce` (in `TVBro.onCreate`) makes Qwant the default search engine once (`Config.DEFAULT_SEARCH_ENGINE_VERSION`) in its partner countries (`RegionDetector`: the SIM or mobile network, else the time zone, else the locale) for users with no saved engine or Google. The built-in home page knows Qwant without the ID: the app takes the URL of its list for a known engine name (`Config.searchEngineUrlOfHomePage`) and sends it back to the page. `Config.canonicalSearchEngineUrl` maps Qwant URLs made by the app with another ID or none to the one of the list. Tests never hard-code the Qwant URL.
- Release signing reads the env vars `KEYSTORE_PATH`, `KEYSTORE_PASSWORD`, `KEY_ALIAS` and `KEY_PASSWORD`. Without `KEYSTORE_PATH`, release builds are unsigned.
- App unit tests use Robolectric (`isIncludeAndroidResources = true`). There are no instrumented tests. Browser core tests use `FakeWebEngine` (registered through `WebEngineFactory.initializeForTests`) and an in-memory Room database (`AppDatabase.setInstanceForTests`).
- Room schemas are exported to `app/schemas` and committed. `AppDatabaseMigrationTest` builds databases of old versions from them, so a database version bump needs its schema exported (it is generated by the build) and a migration test.
- `buildSrc` compiles with `allWarningsAsErrors = true`.

## Module layout

- `:app`: the base application. It holds the browser core (`browser` package, see below), the UI (activities, dialogs, settings), the Room `AppDatabase`, the download service, the WebView engine (`webengine/webview`), the filter lists of ad blocking (`browser/adblock`) and auto-update.
- `:app:common`: an Android library shared by `:app` and `:app:gecko`. It holds the engine abstraction (`webengine/WebEngine.kt` and `WebEngineFactory`), the `Config` prefs, the Room entity models, `AppContext`, `ActiveModel`/`ActiveModelsRepository`, and the cursor widgets (`CursorLayout`, `CursorDrawerDelegate`). Code that both engines need belongs here, because the gecko module must not depend on app-only classes.
- `:app:gecko`: the GeckoView engine (`GeckoWebEngine`, delegates, and a bundled WebExtension under `assets/extensions/generic`). An Android library that `:app` depends on only in `geckoIncluded` variants (`geckoIncludedImplementation`); its keep rules for the app's R8 are in `consumer-rules.pro`.
- `:adblock`: the ad blocker (it replaced the native `ad-block` library in the `adblock-experiment` branch), a dependency of `:app` only (see Ad blocking). `AdblockBenchActivity` of `app/src/debug`, started with adb, measures it on the lists and requests put into its external files dir; build it with `-PdebugNotDebuggable`, ART runs debuggable apps slower. Plain Kotlin without `android.*`, so its tests run on the JVM (`./gradlew :adblock:testDebugUnitTest`; `-PadblockLists=<dir>` also parses the real `*.txt` lists of a directory, which are not in the repository). `parser/FilterParser` reads lists of the Adblock Plus syntax line by line into `NetworkFilter`s and `CosmeticFilter`s; a filter with anything it does not support (an unknown option, scriptlets, procedural selectors, `:has()`, entities as the only domains) is skipped whole and counted in `ParseStats` by reason. `ResourceType` holds the request types as bits of a mask; `POPUP` is a window a page opens (`$popup`), checked by its address with the opener as the page, and like `DOCUMENT` it is not a type of filters without type options. `psl/PublicSuffixList` gives the site (registrable domain) of a host for `third-party`: it loads the asset `adblock/psl.txt`, which `PublicSuffixListCompiler` makes from `adblock/psl/public_suffix_list.dat` (MPL-2.0; a new list is compiled with `-PupdatePsl`, the tests fail while the asset is older; `.gitattributes` keeps its LF line ends), with hash tables of offsets over its bytes and no allocation per lookup. `FilterCompiler` turns the request filters into a `FilterEngine`: flat arrays (flags with the type bits, pattern offsets into one byte pool, domain lists as sorted 64-bit hashes) and four `engine/IndexTable`s (page exceptions, `important`, blocking with the important ones too, exceptions), where a filter is found by the hash of its host (`||host^`) or of its rarest whole token (hashed of its first 16 characters; urls are tokenized in their first 2048), or sits in the small bucket every request checks; a filter found by a token keeps where the token is in its pattern (bits of its flags), so the pattern is checked only where the url has the token; the page exceptions, the exceptions and the important filters are asked only after a blocking filter matched; patterns are matched by `PatternMatcher` without regular expressions, and a regex filter first needs its required literal (`RegexLiterals`) in the url, because `java.util.regex` goes through ICU and JNI on Android. The engine is immutable and thread-safe (a `ThreadLocal` scratch per thread, regexes compiled lazily into an `AtomicReferenceArray`), and its checks catch their own exceptions and block nothing. Element hiding filters (`##`, `#@#`) go into `engine/CosmeticIndex` (built by `CosmeticCompiler`): the selectors of sites by the hash of each domain, the generic selectors that start with a class or an id by the hash of that name, and the rest (high generic) as one list; excluded domains (`~site.com##`) and the exceptions of a site (`site.com#@#`) apply to all of them, and an exception without domains drops its selector everywhere. `FilterEngine.hidingStyles` gives the CSS of a page (its site's selectors and the high generic ones, the latter cached, in rules of 50 selectors, so one bad selector loses only its rule) and whether to ask for the generic ones; `$document`/`$elemhide` exceptions of the page give nothing, `$generichide` only the site's; `genericHidingStyles` gives the CSS of the generic selectors of the classes and ids a page has. `engine/EngineFile` writes it atomically (temporary file, fsync, rename) with a header (magic, `FORMAT_VERSION`, the fingerprint of the lists, CRC32 of the body) and reads it with bulk copies; a file of another version, damaged or truncated is an `AdblockFormatException`. The flags of a filter hold its type bits, its options and, in the top 6 bits, where its token is in its pattern (`FilterFlags`). Raise `FORMAT_VERSION` whenever what is written changes, and `FilterCompiler.VERSION` whenever the parser or the compiler give other arrays for the same lists (the app mixes it into the fingerprint of its lists, so older engine files are built again). `-PadblockLists=<dir>` with a `requests.tsv` (see `tools/adblock-corpus`) also runs `EngineBenchmarkTest`, and with `-PadblockOracle=<file>` (the decisions of @ghostery/adblocker for the same lists and requests, written by `tools/adblock-corpus/oracle.mjs`, which runs it under node outside the repository) `OracleComparisonTest`.
- `buildSrc`: convention plugins `tvbro.android.application` and `tvbro.android.library` (both in `TvBroAndroidModulePlugin.kt`). They apply AGP and set compileSdk, minSdk and targetSdk from `gradle/libs.versions.toml`. The product flavors are declared in `app/build.gradle.kts`. All dependency versions live in that version catalog.

## Key architecture

**Web engine plug-in mechanism.** Each variant has one engine, chosen at build time: the `webengine` flavor sets `BuildConfig.WEB_ENGINE_CLASS` (`...GeckoWebEngine` in `geckoIncluded`, `...WebViewWebEngine` in `geckoExcluded`). Engines register themselves rather than being referenced directly. Each engine class has a `companion object { init { WebEngineFactory.registerProvider(...) } }`, and `TVBro.initWebEngineStuff()` triggers that registration with `Class.forName(BuildConfig.WEB_ENGINE_CLASS)`. `WebEngineFactory` holds that one provider (registering another one fails) and `initialize()`, called from `MainActivity`, initializes it. There is no engine setting and no switching at runtime. **Keep base-app code free of compile-time references to gecko classes.** All interaction goes through the `WebEngine` interface and `WebEngineFactory`. Common code must not check which engine is active either: engine-specific behavior goes through `WebEngineProviderCallback` hooks (incognito data isolation and cleanup, clearing the data of one site with `clearSiteData`/`supportsSiteDataClearing`, failure to create a view, `supportsSetting` for settings only some engines have, see `EngineSpecificSetting`) or `WebEngine` properties (for example `stateFilePrefix` of saved tab state files). `BrowserTab.webEngine` is created lazily; check `isWebEngineCreated` before touching the engines of all tabs. On devices without a hardware AV1 decoder (`HardwareCodecs`) GeckoView turns AV1 off when its runtime starts (`media.av1.enabled` on the default branch, so it is not kept): sites such as YouTube would serve AV1 to it and its software decoder (dav1d) can not keep up on TV chips; WebView already chooses VP9 there.

**Virtual cursor.** The cursor is an optional engine capability: an engine that supports it implements `VirtualCursorSupport` (cursor vs. direct navigation mode, the `CursorDrawerDelegate`), and the UI reaches it only through `webEngine.virtualCursor`. Each engine owns its cursor surface: the WebView engine wraps every `WebViewEx` (and its fullscreen view) in its own `CursorLayout`, Gecko draws the cursor on `GeckoViewWithVirtualCursor` (one view shared by all tabs). The activity's tabs container (`flWebViewContainer`) is a plain `FrameLayout`. When another tab is shown, `MainActivity.onRenderedTabChanged` turns the grab and direct navigation modes off. `CursorDrawerDelegate` (movement, the selection keys, press and grab state) leaves the work to the classes next to it: `CursorRenderer` draws, a `PointerEmulator` talks to the page, `CursorScroller` scrolls at the edges (the engine's `customScrollCallback`, then the "scroll hack", a touch drag) and `PinchZoomGesture` zooms. Input reaches it through the `DPADNavigationEventsAdapter` of the surface, which gives it a direction vector (`setDirection`, each component in -1..1, (0, 0) stops) and forwards the selection keys (`dispatchKeyEvent`): the vector comes from one of two channels, the one engaged last (the other one while it is neutral): the D-pad (the direction keys held and the hats of game controllers, whole steps) or the left sticks (analog: the deflection past a round dead zone with a response curve, only while "Navigate with joystick sticks" is on, `Config.disableMotionAxesDpadNavigation`); the cursor's speed ramps up with the acceleration setting and is scaled by the vector, so a new vector steers it without stopping it. The adapter consumes all joystick motion, since the platform turns unhandled joystick motion into D-pad keys of its own, and ignores the D-pad keys made of motion (`isSynthesizedFromMotion`: a joystick source, or a fallback key of a game controller). While the video takes the D-pad (`BrowserShell.takesDpad`: the video mode, the built-in player, the choice of a stream; the focus stays in the view of the page meanwhile), `MainActivity` gives joystick motion to the platform instead of the views (`JoystickDpadRouter`), so the D-pad of a game controller (mostly a hat) controls the video as the one of a remote does: the platform makes D-pad keys of the hats and the left sticks (repeated while held), which reach the shell as those of a remote. A device stays with the platform until its axes are at rest, so the platform sees the release of its keys (it repeats them until then), and the views get a centered copy of its motion first, so the cursor lets go of a direction it held. The emulator is a finger (`TouchEmulator`) or a mouse (`MouseEmulator`: hover, primary button press and release with the `ACTION_BUTTON_PRESS`/`RELEASE` events WebView needs, wheel scrolling of the element under the cursor; WebView before 137 drops a press whose `actionButton` is 0, which `MotionEvent.obtain` leaves, so the surface tells how its page takes a click, `PointerTarget.mouseClicks`, `WebViewMouseClicks`: for WebView before 137 the engine sets `actionButton` by reflection, `MouseActionButton`, and where that is blocked (Android 9 and 10) gives it the press and release as a finger; 137+ keeps it 0, since with it set Chromium counts double clicks of the OK key), chosen by `CursorDrawerDelegate.pointerMode`; the engines set the mouse for pages in the desktop and tablet views (`SiteView.wide`). The cursor surface is a `PointerTarget` (`CursorLayout`, `GeckoViewWithVirtualCursor`): synthetic hover and wheel events skip its D-pad adapter, and it gives the pixels of one wheel click of its engine; `CursorLayout` gives the mouse events of the cursor straight to the view under them (a ViewGroup finds that view by the cursor position of a mouse event, which events the app makes do not have right on a display with an overridden size: the right half of the page got no clicks). Switching the mode or turning the cursor off cancels the press and the hover in flight and ends the grab mode. The grab mode (the middle button of the cursor menu, left with OK or Back) is a finger held on the page that the cursor drags (it touches only once the cursor moves: a finger standing still would be a long press; one lifted before it moved past the touch slop is cancelled, not a tap) or, for a mouse, where a held button would select text, scrolling: the cursor stands and the directions turn the wheel over the element under it (the menu shows its icon for the mode, the cursor a cross or four arrowheads). A mouse cannot cancel a press (its release is a click, GeckoView keeps the element `:active`), so its press waits until the cursor moves (a drag, pressed where the key went down) or the key goes up (a click), and a long press, which opens the cursor menu, leaves nothing in the page; the mouse hovers the point when the key goes down, so WebView's long press script (`TVBRO_activeElement`, also set by `mousemove` in `generic_injects.js`) finds the link. GeckoView learns the element under a mouse only from its context menu, so its surface asks for a right click on a long press (`PointerTarget.contextClickOnLongPress`, which brings `ContentDelegate.onContextMenu`). GeckoView treats mouse presses as touches on devices in the television UI mode (`PanZoomController.treatMouseAsTouch`, a static flag also used for physical mice); `GeckoViewWithVirtualCursor` turns it off by reflection only while it dispatches a press of the cursor's mouse or of the right button of a mouse of the device (a context menu, not a tap; kept in `consumer-rules.pro`). The menu of a text selection (`MySelectionActionDelegate`, around GeckoView's `BasicSelectionActionDelegate`) shows only for selections of a finger or a mouse of the device (a long press, the mouse being a finger), not of the cursor (`lastPressFromCursor`): the D-pad can not reach it. GeckoView opens no soft keyboard for a field a mouse clicks, so `MyTextInputDelegate` (around its default text input delegate) asks for it after a click of the cursor (`onCursorMouseClick`) that focused a field or went into the focused one, hiding it first: a show request made before the keyboard started the input of the field fails and makes the window drop the next ones.

**Site view and site settings.** Showing a site as on a phone, a tablet or a desktop computer is an engine capability too: an engine implements `SiteViewSupport` (`view`, a `SiteView`: `MOBILE`, the engine's own; `TABLET`, a User-Agent of Android without the sign of a phone and the wide viewport, which sites mostly give their desktop pages; `DESKTOP`, a desktop User-Agent and a wide viewport; WebView builds the User-Agents in `SiteViewUserAgent` from the system one, Chrome of a tablet (`TabletUserAgent`, the reduced User-Agent of Chrome on Android tablets) or of a desktop (`DesktopUserAgent`), with Google Chrome in place of Android WebView in the client hints, and `WebViewPageZoom` writes the wide viewport (see Page zoom); GeckoView switches its User-Agent and viewport modes for the desktop view and gives the tablet view the mobile modes with its own User-Agent ("Tablet" in place of "Mobile") and the width of the desktop view from `page_zoom.js`), reached through `webEngine.siteView`. The tablet view is the default on TV because anti-bot checks (Cloudflare Turnstile, error 600010) refuse a User-Agent of a desktop system in WebView, whose page sees Android in every other way (touch points, no `window.chrome`, no plugins), and take any User-Agent of Android; client hints and `X-Requested-With` do not matter to them (checked on pw.live), and changing the User-Agent by itself when a check comes was not wanted. The view is kept per host (`HostConfig.siteView`, the `SiteView.code` in the column `desktop_view`, where 0 and 1 were the false and true of the two views of older versions; null follows the default; like ad blocking, `HostConfigRepository` keeps these settings of all hosts in memory, loaded before the tabs, so engines ask synchronously). The default is `Config.defaultSiteView` (Settings: Default site view; the desktop or mobile choice of older versions, `LEGACY_DEFAULT_SITE_VIEW_KEY`, is kept), null following the interface: `BrowserController.interfaceSiteView`, set by `MainActivity`, tablet on TV and mobile on phones. A few sites have a view of their own in place of the default (`SiteViewDefaults`, with their subdomains: qwant.com is mobile, its desktop pages are tiny on a TV); a host keeps its own setting only while it differs from that (`BrowserController.defaultSiteViewOf`). The core sets the view before it loads a url or restores a tab; a window a page opens starts in the view of its opener's page; for navigations of the page to another host engines ask `EnginePolicies.siteViewOf` (WebView starts the navigation again, changing its User-Agent only after `shouldOverrideUrlLoading` returned: a change inside it, while a page loads, makes WebView reload in the start of a navigation, which ends the process with a CHECK of Chromium; GeckoView changes the session settings before the load goes on and starts redirects again, once); a page that still starts in the view of another host loads again once (`onPageStarted`). WebView gives Widevine only at `SW_SECURE_CRYPTO` (L3), and sites ask for `SW_SECURE_DECODE` where desktop Chrome gives it (the desktop view; Sweet.tv stopped with an unknown error before it asked for a licence), so `widevine_robustness.js` (`WebViewWidevine`, a document start script in every frame) asks a Widevine request that WebView refuses again with `SW_SECURE_DECODE` lowered to `SW_SECURE_CRYPTO` (license servers take L3, as from desktop Chrome; the hardware levels stay, WebView gives none). The WebView engine always shows Google's sign-in pages in the mobile view (`MobileViewPages`, applied under the view the core set, which it keeps): Google refuses sign-in to WebView with a desktop User-Agent, because WebView sends the app's package in `X-Requested-With`, which current versions do not let an app turn off. The User-Agent setting (Settings, Sites; `Config.userAgent`, Auto, a few browsers of `SettingsNavigator.USER_AGENT_PRESETS` or a custom string) is null by default: the User-Agent then follows the view. One that is set goes to all pages (`SiteViewSupport.userAgentOverride`, set by the core with the view, `BrowserController.onSiteViewSettingsChanged` after a change) in place of the one of the view, which still sets the viewport; WebView keeps the client hints of the view (they can not be dropped once set) and the system User-Agent on `MobileViewPages`. `WebEngine.userAgentString` only tells the current one (for downloads). `CurrentTabState.connection` (`SiteConnection`: no site, secure, http, certificate error; a certificate error stays with its host until the user navigates or the tab shows another host) gives the site button its sliders or the warning sign in `tbColorDsDanger` (`showSiteConnection`), and the header of the site settings its connection line. The built-in home page has no site. The site settings are one view, `SiteSettingsView`, in three variants (`siteSettingsVariant`): the TV `SitePanelView` under the site button, the phone `PhoneSiteSheet` (from the site button of the pill or the site header of the menu sheet) and the site section of the `PhoneMenuSheet` (rows without icons, no Clear site data). Its rows call `BrowserShell.Host` (`toggleSiteAdBlock`, `choosePopupBlockLevel`, `chooseSiteView`, `clearSiteData`, the dialogs are in `MainActivity`); the page reloads and the panel or sheet stays open. Only the TV panel has Player for videos (`chooseSitePlayer`, its dialog in `TvShell`, see Built-in player): the TV Bro player or the site's own for the videos the site puts in fullscreen, chosen as the site view is (a host keeps its own choice only while it differs from the default, `BrowserController.setSitePlayer`; the caption tells which), without a reload (`CurrentTabState.builtInPlayer`, published again when the default changes). Clear site data asks first, with a check box for each kind of data (`SiteDataKind`: cookies and sign-ins, stored data, cache; all checked), and removes the chosen ones of the site (`BrowserController.clearSiteData`), not its settings and history; WebView clears all of them for the whole site at once (`deleteBrowsingDataForSite`), a part of them apart (`WebViewSiteData`: cookies expired one by one, the storage of the origins of the host and its subdomains, and the cache of all sites, as WebView has none of one site).

**Page zoom.** The engines zoom pages only as a pinch does, which stops where the page fits the screen, so a page made for the width of the device (`width=device-width`, most sites) could not get smaller than 100% (1080p TVs are mostly 960 CSS pixels wide). The page zoom (`webengine/PageZoom`: the steps `STEPS`, 33 to 100%) widens the layout of the page instead, as the zoom of a desktop browser does: `assets/page_zoom.js` (in the top frame of both engines; the gecko build copies it into the extension) writes the width of its `<meta name="viewport">` (the width the page asked for, the device's for `device-width`, 980 without a meta, at least the desktop width it is given on screens narrower than 960 CSS pixels, divided by the zoom; a meta of its own for a page without one, added once the document is parsed), keeps the content the page gave its metas (a `MutationObserver`, also for metas the page writes again, React apps do) and gives it back at 100%; the engine fits the new width into the screen, and the media queries of the page see it. The zoom is a setting of the host (`HostConfig.pageZoom`, null for 100%, kept in memory by `HostConfigRepository` like the site view), which the script asks for when a page starts through `WebEngineFactory.pageZooms` (`EnginePageZooms`, set in `TVBro`; never for the home page): WebView synchronously (`WebViewPageZoom`, the `TVBroZoom` bridge, a document start script, which also writes the width of the desktop view, 980, for the desktop and tablet views on screens narrower than 960 CSS pixels (TVs keep the widths of pages at 100%)), GeckoView over the port of the top frame, whose content script asks (`pageZoomRequest`, which makes its port the one of the page). Engines implement `PageZoomSupport` (`webEngine.pageZoom`; both do): `applyPageZoom` gives the page shown a new zoom without a reload (WebView then zooms out as far as it goes, `zoomBy`, since it fits a new width only while the user did not pinch; GeckoView refits by itself), `isZoomedIn` tells whether the user zoomed in past the width of the page (WebView `canZoomOut`, GeckoView asks the script: the visual viewport narrower than the layout), `zoomVisually` zooms as a pinch does and then tells that zoom relative to the width of the page (the script's `visualZoom`, asked once the zoom settled: WebView after 300 ms, GeckoView 300 ms after the fingers of `PinchZoomGesture` are lifted, its `onEnd`). The desktop viewport of GeckoView (`VIEWPORT_MODE_DESKTOP`) ignores the viewport of the page, so a page in the desktop view with a zoom below 100% gets the mobile viewport mode (as the tablet view always does), and the script the desktop width (`GeckoWebEngine.applyViewportMode`, `onPageZoomOf` before a load and a restore, `pageZoomSettings`). The zoom buttons of the cursor menu (TV only; `CursorMenuView.onZoom`) go to `BrowserController.zoomOut`/`zoomIn`: out pinches out while the user zoomed in, else steps the page zoom of the host down; in steps it up while it is below 100%, else pinches in; each step shows a toast with the zoom the page has then (`R.string.zoom_percent`: the page zoom, times the zoom of the pinch after a pinch). The site panel has no row of it.

**Shells: the TV and the phone UI.** `MainActivity` does what both looks share (the browser core, intents, navigation, incognito, downloads, keys and Back) and leaves the look to a `BrowserShell`, which it creates in `onCreate`: `TvShell` (`activity_main.xml`: the bar of the redesign over the page, the virtual cursor; while the bar is open the page stays live under it, slid down by its height, with no focus and no cursor (`VirtualCursorSupport.setCursorHidden`), and another tab the tab strip goes to shows its thumbnail in its place, its engine not switched) or `PhoneShell` (`activity_main_phone.xml`: touch only, the virtual cursor is turned off for every tab view, the bottom `PhoneBar`, which `ScrollAwayBar` slides away while the user scrolls the page down (touches are tracked by the tabs container, `TouchTrackingFrameLayout`), the `PhoneMenuSheet`, the `PhoneSiteSheet`, the `PhoneTabSwitcher`, the `PhoneBookmarksView`, the `PhoneDownloadsView` and the `PhoneSettingsView` over the window, the `PhoneSnackbar` over the page). The shell gets the activity as `BrowserShell.Host` and is told about the engine views, the current tab state, UI events, fullscreen and Back. `UiModeSelector` picks the shell from the Interface setting (`Config.interfaceMode`); on Auto, the phone UI is for devices that are not a TV, have no leanback feature and have a finger touch screen: phones and tablets (the width does not tell them from TVs). Changing the setting restarts the app. A new tab with a blank home page (`Config.HomePageMode.BLANK`) offers the address (`BrowserShell.openNewTab`; the TV bar stays or opens with the focus on it, the phone bar starts editing), as there is nothing to do on the page. The activity is not recreated on rotation or size changes (`configChanges`), so the engine views stay; the phone window is drawn edge to edge and `PhoneShell` applies the insets. On tablets (smallest width from 600dp, `isTablet`; phones in landscape keep full-width sheets) the bottom sheets (menu, site, actions) are at most `ds_phone_sheet_max_width` wide in the middle (`SheetWidth`, decided while they measure, so it follows rotation) and the snackbar `ds_phone_snackbar_max_width`; the pages over the window and the tab switcher (its columns follow the width) take the whole window. The phone settings have no Remote and cursor category (see Settings). The built-in home page has a layout for phones (a CSS media query in `assets/pages/home/index.html`; the copy on the website, used by GeckoView, has to be kept the same); tablets keep the TV layout, with a bigger touch target for the menu of a tile (`any-pointer: coarse`, which TVs do not match).

**Commands and Back.** Browser actions triggered by the user from anywhere (hotkeys of `ShortcutMgr`, voice search) go through `browser/BrowserCommands`, which the activity implements; an action (`Shortcut`) has up to `MAX_BINDINGS` keys (`KeyBinding`: modifiers without the side of the key, a short or a long press) and a key is in one action at most: an action the user never set has its default keys of the remote and of a keyboard without those the user gave other actions, and `ShortcutKeyDialog` moves a key of another action only when it is pressed a second time; a key with only a long press action released early goes to the views after all (`passOn`), and a key that types a character without Ctrl, Alt or Meta is no shortcut while a text field has the focus; the tab actions (new, close, next, previous; Channel +/- of remotes) do nothing while a video is in fullscreen or in the built-in player, where the channel keys are pressed by habit; the buttons of the TV bar call `BrowserController` from the shell. The media keys (play/pause, stop, rewind, fast forward) go to the engine, which runs `assets/media_controls.js` in every frame (players are mostly in iframes of other sites): WebView injects it (started by `webview_media.js`, reporting to `WebViewMediaControls`; WebView runs no document start scripts in frames of about:blank and about:srcdoc, where many players write themselves (player-venom of gidonline and traffilm), so there the script of the parent frame takes the media, the fullscreen, the videos and the subtitles of the same-origin frames inside without the scripts of the app (`frames` of `tvBroWatchMedia` and `tvBroWatchPageVideos`, those without `tvBroMediaCommand`), adding its listeners to them again every second, since a page that writes a frame anew drops them), GeckoView has it in the content script of its extension (`match_about_blank`) (the build copies it there, each frame reports through its own port); the script reports the media of its frame, `MediaFrames` picks the frame (the one with a fullscreen video, else the one that started playing last) and the command goes to that frame only (its reply proxy, its port). GeckoView falls back to its `MediaSession` when no frame reports media. Engines that implement `MediaPlaybackSupport` (`webEngine.mediaPlayback`; both do) also give the state of that media (`MediaState`: playing, position, duration, whether it is in the fullscreen view, whether it is live (a duration of `Infinity`; an unknown one is `NaN`, both null), protected (DRM: its `mediaKeys`, or an `encrypted` event, which comes before the page sets them) and what it plays (`source`, its `currentSrc` with `blob:`: another one is another video), from the reports of the script, `MediaReports`), seek in it, pause it and play it. The TV shell uses them for the video mode (`VideoModeController`, no views): while the page shows a video in fullscreen the cursor is hidden and the keys control the video (Left and Right seek, faster while held, to where the key goes up; OK plays and pauses; Up gives the cursor back, and so does Down while it has no stream of the video to open (see Built-in player), and Back with that cursor hides it again, its callback is above the fullscreen one; the seek bar always tells Up, "↑ Cursor" (`VideoModeController.upHint`), next to what Down does), with the seek bar `VideoOsdView` (it shows for a while when the video mode starts, longer when it has the hint of the built-in player; the title of the tab and "Site player · site" over the timeline, see Built-in player). The shell gets the keys first (`BrowserShell.dispatchKeyEvent`), and in fullscreen Back never reaches the engine views: the back callbacks decide. The videos of the page that other apps can play (`PageVideo`: a file a media element plays, or the manifest of an HLS or DASH stream, never `blob:` media) are found by `assets/page_videos.js` in every frame: the media elements and, through a `PerformanceObserver`, the `.m3u8` and `.mpd` files the page loads, also without the extension when the response has the type of HLS or DASH (`contentType` of Resource Timing, which both engines give; empty for other sites unless the request passed CORS, as players load manifests), and the XML files the page fetches (`application/xml`, `text/xml`: player-venom gives its DASH manifests so, next to VAST ads): those are `PageVideo.Kind.XML`, which the engine reads with the HLS playlists (`HlsPlaylists`, `HlsPlaylist.Dash` for a root element `MPD`) and `PageVideoList` lists as DASH only once read as a manifest, else never, and the subtitle files of the frame, which go with each of its videos (`PageVideo.subtitles`, `PageSubtitle`, of the type of their extension, WebVTT without one): the `<track>`s of its media elements (`showing` while the engine draws them; players that draw subtitles themselves keep their tracks hidden), those players that draw subtitles themselves keep in their state, read through their APIs (JW Player: the tracks of `jwplayer().getPlaylistItem()`, the one shown by `getCaptionsList()`/`getCurrentCaptions()`; video.js with emulated tracks: the `remoteTextTracks()` of `videojs.getPlayers()`; GeckoView reaches the objects of the page through `wrappedJSObject`), those the configuration of a PlayerJS player lists in an inline script (`subtitle:"[Name]url,…"`, ashdi of uakino), and the `.vtt`, `.srt`, `.ass` and `.ttml` files it loads (not those of seek previews, by their names), the one loaded last `showing`, since players load them when they are turned on; WebView runs it with `media_controls.js`, GeckoView in the content script of its extension (the build copies it there), and engines that implement `PageVideosSupport` (`webEngine.pageVideosSupport`; both do) give them as a flow, the reports of the frames kept together by `PageVideoList` (one address once, the variants of an HLS stream not apart: those a master playlist lists, else by their addresses; cleared when the page changes). Where the addresses leave the streams of a frame unclear (`PageVideoList.unclearStreams`: more than one), the engine reads their HLS playlists again (`HlsPlaylists`, with the Referer, User-Agent and cookies of the frame, at most a few per page): a master tells its qualities, a media playlist its duration. The TV bar has a Videos button with their number (dimmed without videos, as Back and Forward are); its `VideosPanelView` lists them, OK opens one in a player app chosen in the dialog of Android (`ExternalVideoPlayer`: the Referer of its frame, the User-Agent and the cookies of the engine, in `Browser.EXTRA_HEADERS` and the `headers` list of MX Player), its options also copy the address and download a file or an HLS or DASH stream (see Downloads); the page keeps playing them as before. When one of them starts to play with sound in the page (`mediaVideo`; the script reports `muted` too, `MediaState.muted`), the TV shell shows a hint plate for a few seconds, `PageVideoHintView` at the top end where the Videos button is, also with the bar hidden; it takes no focus and no keys. Its rules are in `PageVideoHintController` (no views): it shows after the video has played for 3 s while nothing covers the page (the shell checks the bar, panels, menus, screens, the player and fullscreen on each redraw), never for short videos, at most once per page (the tab and its address without the fragment, kept in memory), and only while `Config.pageVideoHint` (Settings, Sites; off by default) is on. Back while it shows (its callback is just above the one of the menu) opens the bar, then the Videos panel at the row of that video (`VideosPanelView.show` with `focusUrl`), so Back, OK plays it in the built-in player; the row of the video the page plays says "Playing on the page". Every Back (the BACK/ESCAPE key, the system back callback, the B button of game controllers, the back button of a mouse; not its right button, which goes to the page: WebView opens the menu of a text selection (Copy…) only on a right click, and mouse users go back with Escape) goes through `BackNavigationEventsAdapter`: one press often comes through more than one of these channels, so an event of another channel within a second of the last one taken is the same press; it also handles the "long press B" mode of game controllers in the direct navigation mode (remotes still go back on a short press). The adapter feeds `MainActivity.screenBackDispatcher`, an own `OnBackPressedDispatcher` of the screen: each overlay has an `OnBackPressedCallback` there that it enables while it is shown, registered in `onCreate` from the lowest priority (the menu) to the highest (the cursor modes, which come from `VirtualCursorSupport.cursorModes`). Voice input (`VoiceSearchHelper`; from Android 11 its own plate at the bottom center of the window, where toasts show, and its errors as toasts of the shell, `BrowserShell.showMessage`) is cancelled by Back: its callback is added after all the others. Never add overlay callbacks to the activity's `onBackPressedDispatcher`: it has one always enabled callback that goes to the adapter. When something else has already handled a Back press in progress (the fullscreen view of WebView leaves fullscreen on BACK down), call `consumeCurrentPress()`. Where the window gives Back to its `OnBackInvokedCallback`s (apps that target Android 16, on Android 16+), WebView registers one for its fullscreen view above the activity's and would leave fullscreen before the app sees Back: while a page is fullscreen, `MainActivity` registers one above all of them (`OverlayBackInvokedCallback`, `PRIORITY_OVERLAY`) that goes to the adapter, so the back callbacks of the screen decide there too.

**Find in page.** Finding text in the page is an engine capability: an engine implements `FindInPageSupport` (`webEngine.findInPage`; both do): `find` highlights all matches ignoring case and goes to the first, `findNext` goes round them, `clearFind` removes the highlights, and `findResult` (`FindResult`: the text, the current match from 1, the number of matches, `MANY` past what GeckoView counts) tells the matches of the last search. WebView uses `findAllAsync` with its `FindListener`, GeckoView the `SessionFinder` of the session (`find` with no text is the next match; results of older searches are dropped). `FindInPageController` (no views, shared by both shells) holds the search: each change of the text searches again, the result shown is only that of the text in the field, it ends when another tab is shown and runs again when the page changes (another address without the fragment, or a load finished; the count is blank while the page loads), and the last text comes back when the bar opens again. It opens from the ⋮ menu of the TV bar, the `PhoneMenuSheet` and the Find in page hotkey (`Shortcut.FIND_IN_PAGE`, Ctrl+F by default, `BrowserCommands.findInPage` → `BrowserShell.showFindInPage`). The TV shell shows `TvFindBarView` over the top end of the page (the bar closes before it opens, and opening the bar ends the search; not over the screens, the player or fullscreen): the field (with a mic, `VoiceSearchHelper`), the count, previous and next (dimmed but focusable without matches) and close; Down gives the page the focus and Back in the page brings it back to the bar, Back on the bar closes it (its callback is just above the one of the page video hint). The phone shell shows `PhoneFindBar` in the place of the `PhoneBar` (invisible meanwhile, and nothing slides away), above the keyboard; Back closes it.

**Address suggestions.** While the address is edited, both shells suggest pages of the browsing history and, after them, searches of the search engine. `AddressSuggestions` (no views, shared by both shells, `AddressSuggestions.Store` is the `HistoryRepository`) loads the whole history when the editing starts and searches it in memory, as the history screens do: one entry per url (a trailing slash makes no other), its visits weighed by recency (`recencyWeight`); `rank` orders by how the text matches (the site starts with it, the address starts with it, the first word starts a word of the title or the address, each word found anywhere, ignoring case also outside ASCII) and then by that score, at most `MAX_ROWS`. Nothing is suggested for the text the editing started with. The searches (`Row.Search`, the pages are `Row.Page`) come from `AddressSuggestions.SearchSource`, which is `SearchEngineSuggestions` (`browser/search`): only while `Config.searchSuggestions` is on (Settings, Search; on by default), never in incognito mode, and only for texts `SearchSuggestRules.shouldAsk` takes for a search (not one with a scheme, a path, a port or a host with dots, not shorter than 2 characters unless it is an ideograph, not longer than 100), so addresses stay on the device. `SearchEngines.suggestUrlOf` gives the address of the suggestions of the engine: each engine of `Config.SearchEnginesURLs` has one in `Config.SearchEnginesSuggestURLs`, the user's own engine `Config.customSearchSuggestUrl` (kept with the host of the engine it was given for, blank again once the engine is of another host), else that of the engine of the list its host belongs to (google.com.ua). `SearchSuggestClient` asks it with `AppProxy.open`, without cookies (3 s timeouts, at most 64 KB), and `SearchSuggestParser` reads OpenSearch suggestions (`["text", ["suggestion", …]]`); an engine that does not answer gives no rows and no message. `SearchSuggestLimiter` (one for the process) keeps the requests few, so an engine does not take the device for a robot: at most 30 a minute, and an engine that refuses (429, 403: `SearchSuggestRefusedException`) or fails twice in a row is not asked for 10 minutes (`asks` is false meanwhile, so no rows wait for it). The engine is asked 300 ms after the last change of the text, an answer for an earlier text is dropped, the answers are kept while the address is edited, and until an answer comes the searches shown that still start with the text stay. `merge` makes the list: the pages, then the searches, 3 rows each when both have more, else one takes the rows the other leaves; while the engine is asked its rows are left free, so the pages do not go when it answers. `InlineAddressCompletion` completes the field inline: after text added at the end (never after a deletion, never text with spaces; also while the keyboard composes a word there, which Gboard does in these fields) it appends the rest of the address and selects it, posted after the edit, since the keyboard places the cursor after the text it put in and would drop a selection made in the `TextWatcher`; the fields are `AddressEditText`, whose input connection turns the Backspace of a soft keyboard (`deleteSurroundingText`, which deletes before the selection and keeps it) into the removal of the completion shown and removes it before the keyboard sets or commits its word (which replaces the word, not the selection); while the text is in the site part it completes the site (`yo` → `youtube.com`), after a '/' a whole url, in the form typed (with a scheme, with www., or without both). The field submitted with the text of the completion opens its url (`urlFor`, the scheme of the history: an http-only site stays on http) through `Host.navigate`, other text goes to `search` as before. `AddressSuggestionsView` draws the rows (not focusable, so the focus stays in the field; a search has the search icon, no address and the arrow `ibFill`; the row chosen with the D-pad stays chosen by its `id` when the list is drawn again with it, as the searches come after the pages): under the address of the TV bar (placed by `TvShell`, `ds_suggestion_row_bg`), above the phone bar with the best next to it (`bestAtBottom`); rows without room are cut, not squeezed. On TV the D-pad chooses a row from the field (`ActionBar.etUrlKeyListener`: Down and Up, Left and Right go back to the text, OK and Enter open the chosen one (a search is searched), Right on a chosen search puts its text and a space into the field to go on with it (`fillSuggestion`, `InlineAddressCompletion.replaceText`; on the phone the arrow of the row does), Back goes back to the text, its callback just above the one of the menu); the keyboard takes the D-pad while it is shown, so the rows are reached after Back hides it. The fields of both bars have `flagNoExtractUi`, so a fullscreen keyboard (Gboard in landscape on phones) does not cover the list.

**Ad blocking.** The engine of `:adblock` decides; `browser/adblock/AdBlockService` (one per browser process, `AppContainer.adBlock`, started by `TVBro.initAdBlocking`, never in `:downloads`) keeps it: `filesDir/adblock` holds `lists.json` (`FilterListsStore`: the lists turned on, the address of the user's own list, the updates of each list), `lists/<id>.txt` (the downloaded lists, kept to build the engine again without the network) and `engine.bin`. At start it loads `engine.bin` when its fingerprint (the compiler version and the files of the enabled lists) fits, else builds it from the lists in the background; `BrowserController` waits for the load (not a build) up to a second before restoring tabs. The engine is replaced by a write of a volatile reference. Lists (`FilterListCatalog`: EasyList, EasyPrivacy, one regional list, the system language's by default, and the user's own one) are downloaded by `ListFetcher` with conditional requests when their `! Expires:` comes (1 to 7 days), right away on the first start, otherwise 30 s after start and then every 6 h while the process lives; a failed download keeps the list, its date and the engine and is tried again after 1 h, 6 h, then a day; a page of HTML is a failure. The service also deletes the file and the prefs of the native library. Engines never ask the callbacks of a tab: the app sets `WebEngineFactory.adBlocker` (`EngineAdBlocker`, implemented by `AppEngineAdBlocker` with the `HostConfigRepository` given once: the setting of the host of the tab's page, else `Config.adBlockEnabled`, never on the home page), asked for every request of every tab on the engine's threads. WebView gives it the Accept header (`ResourceType.guessFromAccept`: a mask of the types a request may be, never a ping) and the page of its tab: `WebViewEx` keeps the url of the main frame request before `onPageStarted` comes (and the page again when a navigation becomes a download); a blocked request gets an empty 403. GeckoView gives it the WebExtension type, the frame and the top page (`frameAncestors`) from `background.js`, whose one port for all tabs (`AppWebExtensionBackgroundPortDelegate`, registered once for the extension) answers each request it holds (1.5 s timeout); main frames go there only while filters block pages (`FilterEngine.blocksPages`, sent as a config message). The script tells the top frame of the tab what it blocked (`tabs.sendMessage`), and `content.js` passes it over the port of its session to `TabEngineEvents.onBlockedAd` of that tab; WebView counts the blocks of the current tab only. Element hiding (no setting of its own, it follows the ad blocking of the tab's page; a frame of about:blank or about:srcdoc gets the selectors of that page) is `assets/element_hiding.js` in every frame of both engines (the gecko build copies it into the extension): it puts the CSS of the page into one `<style>` at once, then collects the classes and ids of the elements (a `MutationObserver`, batches every 50 ms, each name once, at most 20000) and adds the CSS of their generic selectors. WebView runs it as a document start script (`WebViewElementHiding`, in `onPageStarted` and `onPageFinished` where DOCUMENT_START_SCRIPT is missing) that asks the synchronous `@JavascriptInterface` `TVBroHiding`, so the CSS is there before the elements; WebView runs no such script in frames of about:blank and about:srcdoc, so the script of their parent hides their elements (`api.frames`). GeckoView runs it in its content script (`match_about_blank`), which asks over the port of its session; `AppContentScriptPortDelegate` answers on a thread of its own, so an ad can show for a moment. Popups (`EngineAdBlocker.shouldBlockPopup`: the `$popup` filters and those that cancel navigations, see below, with the opener as the page, under the ad blocking setting of the opener's page; ad scripts often open a window at `intent://` to Chrome and send it to the ad site when that fails) are checked by the first web address of the window, after the popup blocking level let it open: GeckoView checks the address of `onNewSession` and blocks the window as the level does (`onBlockedDialog`); a window opened at about:blank (`GeckoWebEngine.popupOpener`) and every window of WebView (`WebViewEx.popupOpener`, set in `onCreateWindow`, which gives no address; checked with the first main frame request) are already tabs then, so the engine denies the load and calls `TabEngineEvents.onPopupPageBlocked`: the core shows the tab that opened it (`BrowserTab.openerTab`, kept in memory only) and closes it, counting a blocked popup there. A url the app loads (`loadUrl`) clears the opener, so a window whose page never navigated is not checked later. Ads also take the tab itself away (a click runs `location = ad`, after an `intent://` to Chrome fails): a navigation of the main frame that the page starts (WebView `shouldOverrideUrlLoading`, which the app's own loads skip, with the page that started (`currentOriginalUrl`: `view.url` is already the new address there); GeckoView `onLoadRequest` that is not `isDirectNavigation`, in the current window) is cancelled when `EngineAdBlocker.shouldCancelNavigation` says so (`FilterEngine.matchNavigation`: a `$document` filter, or a filter of a whole host (`||host^`, no options but the party) when the host is of another site than the page, as the strict blocking of uBlock Origin; exceptions without type options and `$document` exceptions of the page or the target let it go): the page stays, its history too, and a blocked ad is counted. The Enhanced Tracking Protection of GeckoView is a setting of its own (`Config.trackingProtection`, `EngineSpecificSetting.TRACKING_PROTECTION`), applied when a tab is attached, reloaded or loads a url, and its blocks are not counted.

**Proxy.** The browser can go through an HTTP proxy (https sites through it with CONNECT) or a SOCKS5 one (Settings, Advanced; `Config.proxyEnabled`/`proxyType`/`proxyHost`/`proxyPort`, the login in `Config.proxyUsername`/`proxyPassword`, which are kept in the prefs file `credentials.xml`, left out of backups by `backup_rules.xml` and `data_extraction_rules.xml`). `Config.proxy` (`net/ProxySettings.of`) is the proxy in use: null while it is off or its address is not complete; only an HTTP proxy has a login (WebView can not log in to a SOCKS one). Local addresses never go through it (`ProxySettings.BYPASS_DOMAINS` and `BYPASS_NETWORKS`, the same rules for the engines and the app), and nothing falls back to a direct connection when it fails: pages show the network error. `net/AppProxy` (in `:app:common`) holds the proxy of the process (`AppProxy.settings`); `browser/ProxySetup.start` sets it from the settings first in `TVBro.onCreate`, and `ProxySetup.apply` (called by `AppSettingsStore` after each change) gives a changed proxy to the engine (`WebEngineFactory.applyProxy`, `EngineSpecificSetting.PROXY`) and reloads the current page, so it applies at once. Engines apply `AppProxy.settings` in `initialize`, before any tab loads: WebView with `ProxyController` (`WebViewProxy`, no `DIRECT` rule; it checks the rules itself), GeckoView with the `network.proxy.*` preferences on the default branch (`GeckoProxyPrefs`, not kept, the old defaults given back when it is turned off, `failover_direct` off). Never touch `ProxyController` or `WebViewFeature` before `initialize`: they load WebView, and the incognito process must give it its data directory first. Both engines answer the login request of the proxy with the saved login unless it was refused (`WebViewEx.onReceivedHttpAuthRequest` for the proxy host, `MyPromptDelegate.onAuthPrompt` with `Flags.PROXY`). The app's own requests (filter lists, updates, favicons, downloads) open connections with `AppProxy.open`, never `URL.openConnection()`: a proxy given to the connection is the only one the HTTP client of Android (OkHttp 2.7) uses, while after the proxies of a `ProxySelector` fail it tries a direct connection. `AppProxy.install` sets the default `ProxySelector` (web schemes only; other sockets connect directly) for Media3, which opens its connections itself, so the built-in player may go directly when the proxy is down, and the default `Authenticator`, which answers only the proxies connections were opened with, once per request: OkHttp asks again without end while the proxy refuses the login of a tunnel. The login is never put on a request (`Proxy-Authorization`): the client does not move it to the CONNECT, so it would go through the tunnel to the server, also after a redirect to https. That client answers a 407 of a tunnel on the same connection, so the app's https requests through a proxy with a login need a proxy that keeps the connection after the 407 (Squid does). The downloads process does not see later changes of the settings: the proxy goes with each start and resume command (`DownloadCommands.KEY_PROXY`) and stays with that download (`HttpDownloadTask`). `Utils.isLocalNetworkUrl` still resolves the hosts of pages locally, and external players get no proxy.

**Browser core and engine callbacks.** `browser/BrowserController` (an `ActiveModel`) owns the tabs: their list, the current tab, persistence, opening/closing/switching, navigation, the engine events and the browsing history. It knows nothing about views: an activity attaches itself as `BrowserController.TabViewHost`, which creates engine views (`createTabView`) and provides the UI part of the engine callbacks (`uiHost`). The engine of the current tab gets a `WebEngineCallbacks` in `onAttachToWindow`; it is composed of three parts, all in `webengine/WebEngineCallbacks.kt`: `TabEngineEvents` (implemented by the controller), `EnginePolicies` (`TabPolicies`: dialogs and new windows blocking, the site view; ads are asked of `WebEngineFactory.adBlocker`, see Ad blocking) and `EngineUiHost` (implemented by the activity: menus, dialogs, fullscreen, page scrolling, permissions and file picking with result callbacks, downloads as `DownloadRequest`). The callbacks are set only while the tab is current, so background tabs report nothing. The UI renders `BrowserController.currentTabState` (`StateFlow<CurrentTabState>`) and handles one-time `BrowserUiEvent`s from `uiEvents` (a channel with a single collector). Other core pieces: `HomePageLinks` (links of the built-in home page), `VisitedHistoryLogger`, `HomePageUrl` (resolves `about:home`, engines never get the alias), `UrlRouter`/`UrlInputResolver`/`PopupBlockPolicy`, `Downloads.kt`. Activities start other activities and ask for permissions through `utils/launchForResult` (the ActivityResult registry), never with request codes.

**State models.** Screens keep state in `ActiveModel` subclasses (for example `BrowserController`, `SettingsModel`, `AutoUpdateModel` and `DownloadsModel`). They get them through `ActiveModelsRepository.get(Model::class, activity)`, not through AndroidX ViewModel. A model is released when every activity using it finishes. Older observable state uses the custom `utils/observable` types (`ObservableValue` and `ObservableList`); new code uses `StateFlow`/`Flow` (with immutable values: a `StateFlow` does not emit a value equal to the previous one).

**Tabs.** `BrowserTab` (in `:app:common`, engines get it) is a tab in memory: its engine, thumbnail and page state; it is read and changed on the main thread only. The database keeps `TabEntity` snapshots (`toEntity()`/`fromEntity()`), and `browser/TabFilesStore` keeps the files of tabs (engine states, WebP thumbnails), getting and returning file names without touching tabs. `BrowserController.saveTab` takes the snapshot when called and enqueues the write in `tabWrites`; the queue runs on the main thread, so the id and the file names given by earlier writes are applied there. A tab is saved when it stops or starts being the current one and when the activity pauses. `BrowserController.navigate` sets `tab.url` before the page starts; a navigation that becomes a download (any `EngineUiHost.onDownloadRequested`, seen by the controller through its wrapper of the UI host) gives the tab back `BrowserTab.pageUrl`, the page it shows (`about:blank` if none yet), so a restored tab does not download the link again.

**Bookmarks.** `FavoriteItem`s are kept in folders: a folder is an item without a url, its contents point to it with `parent` (0 is the top level, `FavoritesRepository.ROOT`). The bookmarks of the built-in home page are the Home page folder (`FavoritesRepository.HOME_PAGE`, no row in the table: they are marked with `homePageBookmark`, hold no folders and are not in the top level). In a folder, folders come first, then bookmarks, each by `order` (the newest first among equal orders): new items go to the top, new home page bookmarks to the end. The home page shows the bookmarks of its folder in that order (a link's `order` is its place on the page) and leaves out those it has no room for; the user can choose another folder for it, or the top level (Settings, Search and home page; `Config.homePageBookmarksFolder`, the Home page folder by default and when the chosen one is gone, `FavoritesRepository.existingFolder`): it then shows the bookmarks right in that folder, not in its folders, a tile added from the page goes to the end of that folder, and the suggestions of the first start fill only the Home page folder. `HomePageLinks.load()` is called after bookmarks change. Use the repository (`add`, `moveTo`, `move`, `delete` with the contents of a folder), not the DAO. What the bookmarks screens show and do is in `BookmarksNavigator` (no views: a stack of screens, a folder, the form of a bookmark or folder, the choice of a folder, the search of all folders, the bookmarks files in Downloads and the ways to import one, rendered through its `Host`); the shells only draw it. Export and import use the HTML bookmarks file of Chrome, Firefox and Edge (`data/BookmarksHtml`, a pure reader and writer; the Home page folder is marked with `TVBRO_HOME_PAGE` on its H3); `FavoritesRepository.importBookmarks` holds the rules of the new folder and merge imports, and `DeviceBookmarkFiles` (the navigator's `Files`) saves to and lists Downloads as downloads do (MediaStore from Android 11, which lists only the app's own files there) and opens the system picker. The TV bar keeps Bookmarks, Downloads and Incognito as buttons; History, Send to this TV and Settings are in the `PopupMenuView` of its ⋮ button (`TvShell.showMoreMenu`). The TV shell shows the bookmarks in `BookmarksPanelView`, under the star of the bar, with the row menus in a `PopupMenuView` (both are `AnchoredOverlayView`s, which keep the focus inside them while open). The phone shell shows it in `PhoneBookmarksView` over the whole window, with the actions of a row in a `PhoneActionsSheet` and reordering by dragging; the Bookmark button of the menu sheet adds the page, or opens its bookmark.

**Downloads.** `DownloadService` runs in its own process (`:downloads`, see the manifest), so downloads go on while the browser switches between its normal and `:incognito` processes (which kill each other) and both can start them; `TVBro.onCreate` initializes only the database and the notification channel there, and nothing in processes the app does not know (`AppProcesses`: the content, GPU and other processes of GeckoView, which Android also creates the `Application` in; an unreadable name is taken for the browser). The browser processes reach it through `AppContainer.downloadService` (`DownloadServiceClient`): `DownloadCommands` (start, cancel, pause, resume) in `Message`s of a `Messenger`, which wait until the service is bound; the activity keeps it bound only while it is started and a download is in progress or a downloads screen or panel is shown (`DownloadServiceNeed`; a row a dead process left in progress counts, so the service starts and marks it), otherwise the process does not run. While a browser is bound, the service is started too (`onBind`/`onRebind`), and it stops itself only when nothing is bound, running or waiting for the database (`stopIfIdle`, a second after the last `onUnbind`): the launcher unbinds right after it sends a command, and a service that was only bound was destroyed before it handled it (its successor took the new row for one a dead process left). Nothing comes back through the binder: the database is the only state. `DownloadLauncher` inserts the row of a new download (`Download.status`: in progress, paused, done, failed, cancelled; `error` keeps a reason, see `Download.Error`) before it sends the start; the service writes the progress every second and the end, and on its start makes the downloads a dead process left in progress paused (resumable) or failed. `AppDatabase` is opened with multi-instance invalidation, so the Room flows of the browser processes see these writes; `DownloadsModel` turns them into `DownloadItem` snapshots with speeds and `DownloadEvent`s (a download ended). Responses a web engine fetched itself (GeckoView) and blob data cannot cross processes: the launcher copies them into a reliable pipe whose read end goes with the start command (its own copy is closed without a status, see `DownloadServiceClient`); a cut pipe fails the download. WebView tells only the address of a download, so the contents of a `blob:` download come from the page (`WebViewBlobDownloads`, `assets/blob_downloads.js`, a document start script of every frame; none without `WEB_MESSAGE_LISTENER`, where the download fails): each frame says hello to the `tvBroBlobs` channel, the frames of the origin of the address (`BlobFrames`, of all views, since a window the page opens is a view of its own; main frames first) are asked for its size, type and name (the `download` attribute of the link clicked or `click()`ed, or the name of a `File`: WebView gives no name for blobs), then for its bytes a chunk at a time as the pipe takes them (array buffers with the id of the transfer in their first 4 bytes, base64 text where `WEB_MESSAGE_ARRAY_BUFFER` is missing); the script keeps the blob of an address for 30 s after the page revokes it, as pages revoke it right after the click. Addresses a service worker serves (Telegram Web K's `/k/d/<id>`) can not be downloaded: the download service asks the server for them. `HttpDownloads` requests files (redirects followed by hand, cookies only to the host of the site, no content encoding); a download is resumable when the server gives byte ranges and its size: pause keeps the file (pending in MediaStore on Android 11+) and resume asks for the rest with Range and If-Range (`decideRange`). Files go to the public Downloads directory, or to a folder the user chose (Settings, Advanced) with the picker of the Storage Access Framework (`utils/DownloadFolder`: a tree uri in `Config.downloadFolderUri` with a persisted grant, which the downloads process shares; the option is there only where some app takes `ACTION_OPEN_DOCUMENT_TREE`, many TVs have none). The folder goes with each start and resume command (`DownloadCommands.KEY_FOLDER`, as the proxy does); `DownloadLauncher` sends it only while the grant is kept and the folder is there (a removed USB drive), else tells the user and the file goes to Downloads; a lost grant does not come back, so it also resets the setting (the service falls back too when it can not create the document), and asks for the storage permission of Android 10 and older only for Downloads. A document is created with the type of its extension (providers add the extension of the type to other names) and loses resuming when its provider gives no seekable file. `Download.filepath` is one of three kinds, told by the path and not by the version of Android (`utils/DownloadFiles`): a path in Downloads (before Android 11), a MediaStore uri (Android 11+) or a document of the chosen folder (deleted with `DocumentsContract.deleteDocument`, never pending); go through `DownloadFiles` for its file. Cookies are never stored: resume and Download again take them from the engine of the current tab (`BrowserShell.Host.downloadCommands`). Incognito downloads keep no `referer` (the page they came from). What the downloads screens show and do is in `DownloadsNavigator` (no views; looks: the TV panel of the bar with the latest downloads, the TV screen and the phone page of all downloads with filters by `Kind`), its `Device` is `DeviceDownloads` (open, install, share, the Downloads folder through `DownloadFileActions`; Android TV sends intents no app handles to stubs that only show a toast, they count as none). The TV shell shows `DownloadsPanelView` under the Downloads button of the bar (with a badge of the active downloads) and `DownloadsScreenView` over the window; the phone shell shows `PhoneDownloadsView`; rows are bound by `bindDownloadRow`, captions made by `DownloadRowText`. **Streams.** The TV shell saves HLS and DASH streams of pages (`PageVideo.Kind.HLS`, `DASH`) as MP4 files, without decoding: `browser/StreamDownloads` reads the playlists or the manifest in the browser process (Media3's `HlsPlaylistParser` and `DashManifestParser`, the headers of the page) for the qualities, the best first, the size estimated from the bitrate and the duration (one is downloaded at once, more are offered in the menu of the row of the Videos panel or in a page of the player's panel): the HLS variants, each with its audio inside or the audio rendition of its group (`audioOf`: the language of the system, else the default one), and the heights of the video of a DASH manifest, each with the representation of H.264, else H.265, else another codec the muxer takes, and the default audio (`DashPlan.defaultAudio`). It refuses live (no end, a dynamic manifest), protected (DRM, SAMPLE-AES: `HlsPlan.isProtected`, since Media3 drops SAMPLE-AES with an identity key; any ContentProtection of a manifest, which Media3 drops when it can not read it) and other streams with a toast of the reason (`Download.Error.LIVE`, `PROTECTED`, `FORMAT`). The chosen quality is `StreamSpec` (the media playlist of the variant and of its audio, or the manifest with the ids of the representations, the height, bitrates, the duration), kept as json in `Download.streamSpec` (the `stream` column; `url` stays the address the page gave), so the service takes `VideoStreamDownloadTask` for the row on start and resume, and Download again saves it again. The task (`service/downloads/stream`) reads the playlists or the manifest again each time (fresh addresses) and plans them (`StreamPlan`: a `TrackPlan` of the video and one of the audio when it has segments of its own, each with segments, byte ranges, AES-128 keys and IVs, init segments and parts (HLS discontinuities, DASH periods, where the representations are found again by id, else by height or language); `HlsPlan`, `DashPlan`: a representation of one file is one segment), then downloads the segments of both tracks in the order of their time, decrypted, each into a file of its own in `StreamWorkDir` (`noBackupFilesDir/stream-downloads/<id>`, named by track; a `.part` file until it is whole; a `plan` file drops the segments of another plan), with `HttpDownloads.fetch` (the redirects, retries, proxy and headers of `open`, without touching the row); a segment is tried 3 times. Resuming downloads only the segments that are not there, so stream rows are resumable; `bytesReceived` counts the bytes of the segments and `size` is an estimate from them, kept above them (the captions say "of about"). When all are there, `size` is set to `bytesReceived` (the row says Saving the video) and `StreamMuxer` packs them into the file, chunk by chunk (a part of the video with the part of the audio): Media3's extractors, found by sniffing (`TsExtractor`, `AdtsExtractor`, `FragmentedMp4Extractor` after the init segment, `MatroskaExtractor`), read the video and the audio side by side (the audio inside the video is dropped when the audio has a source of its own), one `TimestampAdjuster` from the start of the chunk keeps their distances, and the samples go to Media3's `Mp4Muxer` (`media3-muxer`; a regular MP4, `FragmentedMp4Muxer` where the output can not seek) in the order of their timestamps, after all tracks are added (the fragmented muxer takes none later), each segment deleted once read; a track the muxer does not take (MP3, AC-3 audio) fails it with `FORMAT`. A stop while it packs deletes the file (resume downloads the deleted segments and packs again). `DownloadFileActions.deleteFile` deletes the folder of the segments too, and the service deletes those of ended downloads when it starts. Cookies go only to the host of the playlist, as for files (the built-in player sends them to all hosts).

**Built-in player.** The TV shell plays the videos of pages (`PageVideo`) in a player of its own, on Media3 (ExoPlayer: HLS, DASH and files), because the engines draw video into the window (1080p on a 4K TV, at a high CPU cost in WebView) and the player gives it a `SurfaceView` layer of its own. It is a view over the whole window of the browser activity, `PlayerScreenView`, in the process of the page (normal or `:incognito`), not an activity. `player/NativePlayer` (no views) wraps ExoPlayer: it requests the video with the headers of the page (`ExternalVideoPlayer.headers`: the Referer of its frame, the User-Agent and the cookies of the engine) and tells its state as a flow. The keys are those of the video mode (a `VideoModeController` of its own, whose host takes Up and Down): Left and Right seek, OK plays and pauses, Down (and the Menu key, which a Shield and many TVs keep to themselves) opens the video settings (`PlayerPanelView`, a panel of the full height at the end of the screen, a page at a time: each row with its value opens the page of its options, the chosen one checked): the quality, the audio track, the subtitles and the speed (`PlayerTracks`; the subtitles are those of the stream and the files of the page, given to Media3 as sidecar WebVTT with the headers of the video, `NativePlayer.subtitleConfigurations`, the one the page shows chosen at the start; the caption channel Media3 gives every HLS stream of MPEG-TS that declares none, mostly empty, is Captions in the video and listed last), the repeat of the video (`NativePlayer.looping`, off for each video, not for live streams), picture-in-picture, Player for this site (the effective player as its value), Open in another app and Download (a file, or an HLS or DASH stream saved as an MP4 file, see Downloads; not for live or protected media; the qualities of a stream are a page of the panel, the one that plays checked; the player plays on, the toasts of downloads show at the top meanwhile), which the seek bar tells with the hint "↓ Video settings"; for the video the page plays Up gives it back to the page ("↑ Site player", see below), for another one Up does nothing; the media keys of the remote go to it while it is open (`BrowserShell.onMediaCommand`); Back closes the panel a page at a time, then the player (its callback is the highest). OK on a row of the Videos panel opens it (the video the page plays goes on from where it is; its options keep the other app); in the video mode Down takes the fullscreen video of the page there, from where it is, when the engine knows its stream (`PageVideosSupport.mediaVideo`: `PageVideoMatch` of what `media_controls.js` reports the media plays and the videos of its frame; the seek bar shows the hint; for media the page streams itself the only stream of its frame, or the only one whose playlist lasts as long as the media); when it is not clear which of the streams of the frame it plays (`PageVideoMatch.choices`, those of the same length as the media first, `sameLength`, with the durations of their playlists), the hint is the same and Down opens the choice of the stream over the fullscreen video (`TvShell.showMediaVideoChoices`: a `PlayerPanelView` of the shell, its rows the files of the streams, by their folder where two have the same name, `PageVideoRowText.fileNames`, with a badge on those of the same length and the kind, height, duration and server under them, `choiceCaption`): the page pauses and its video mode is off meanwhile, OK goes on with the chosen stream in the built-in player from the second the page paused at, Back stays with the player of the page (which plays on if it played). The page pauses its media (`MediaPlaybackSupport.pausePlayback`) when the player opens; a page in fullscreen stays so under the player, its video mode off meanwhile (`VideoModeController.suspended`: no seek bar and no keys, set before the pause, which would show the bar over the player). How the player closes (`PlayerScreenView.Exit`) says what the page does then: for the video the page plays (`show` with `pageMedia`) Up seeks the page to where the player was and plays it (`MediaPlaybackSupport.resumePlayback`, the `play` command of `media_controls.js`), still in fullscreen; Back seeks it there and leaves fullscreen paused; the picture-in-picture window and another app leave fullscreen too (the video mode stays off until fullscreen is gone); another page shown (`BrowserShell.showPage`: a new tab, a link of another app, a voice search) closes it, the page it covered paused (`Exit.PAGE`). The player takes the focus only for its menu and its error and gives it back to the view that had it, the fullscreen view of the page (WebView's own view is hidden behind it). An error shows a card over the dimmed video (`PlaybackFailure`: the status of the server, the network, the format, DRM, in words) with Watch in the site player (the video of the page goes on there; Back to the page for another video) and Open in another app. The seek bar of both players is the same `VideoOsdView`, a band across the bottom of the screen under a gradient (never narrower, and it stays while paused): the title of the tab, then what plays it (TV Bro player, the height of the video track playing, `NativePlayer.State.videoHeight`, the kind and the site of the tab, `PageVideoRowText.playerCaption`; Site player and the site for the page, `sitePlayerCaption`), the round glyph of what OK does (play while paused, pause while it plays, the direction of a seek), the position, the progress (`VideoProgressView`: played in the selected color, loaded, `MediaState.buffered`, which only the built-in player tells, refreshing its state every second; a seek shows the way from where the video is to its target, a mark where it is and the bigger thumb with the focus ring, and a bubble over it with the target and its distance) and the duration; a live stream (`MediaState.live`) shows its badge and the distance of a seek instead. The first three times it shows a video (at its first frame, `Callback.onFirstFrame`, so not over the error of one that does not start; `Config.builtInPlayerIntroShown`; the users who chose "Don't show again" for the dialog it replaced count as done), a toast at the top tells what it is for (smoother, the full resolution of the screen), without pausing the video (`NotificationView.show` with `top`, above the player by its elevation). Until its first frame the screen is transparent and dimmed, so the paused frame of the page in fullscreen shows through under the spinner (Gecko draws its pages into a `SurfaceView` under the player's; WebView draws in the window, where the surface of the player cuts its hole, so a Shield shows black there and the emulator the page), then black around the video. The surface of the player is a media overlay (`setZOrderMediaOverlay`): surfaces of one layer are stacked in the order they were made in, and GeckoView makes its own again when the activity comes back (from the picture-in-picture window, which put it over the video on a Shield). It is there only while a video is shown: the screen hides its `PlayerView`, which hides its `SurfaceView` too and so drops the surface; a surface that is only under a hidden parent keeps the last frame, which showed under the next video until its first frame (and under the error card). The user calls it TV Bro player (`R.string.built_in_player`); the page's is the site player. **One player:** the TV shell gives a video the page puts in fullscreen to the built-in player by itself, from the same second, by the rules of `PlayerChoice` (no views, the time given; the first rule that applies): the site leaves videos to its own player (`BrowserController.prefersBuiltInPlayer`: `HostConfig.builtInPlayer`, kept in memory by `HostConfigRepository` like the site view, null following `Config.builtInPlayerByDefault`, the Player for videos of Settings, Sites, TV only; chosen in the player's menu, Player for this site: Default, TV Bro player or Site player, which takes the video back to the page at once, and in the site panel, Player for videos, which applies to the next fullscreen also on a page that kept its videos, `PlayerChoice.siteChoiceChanged`); the video is protected; no stream of it is known (`PageVideoMatch.video`, also when it may be one of several); it is shorter than 60 s and not live (ads, previews); or what the rules need came more than 1 s after it went fullscreen (the page played it meanwhile, a switch would surprise) — the page keeps it then; else the built-in player opens (`auto`), the page in fullscreen under it. The window of 1 s starts again when the element plays another video (`MediaState.source`: an ad, then the film; also a video that starts only after the page went fullscreen), and each fullscreen is decided anew; nothing is decided while the built-in player is open, and a page whose video went back to its player (Up, or a failed start) keeps its videos until another page (the tab and its address without the fragment). `PlayerChoice.down` tells what Down (and the Menu key) does in the video mode of the page: the built-in player for a known stream, the streams it may be, or the cursor (none known, or protected). A player the rules opened that shows no frame within 5 s or meets an error before its first frame (`PlayerStart`; that error is not shown) closes itself (`PlayerScreenView.Exit.FAILED`): the page plays the video on from where it was, and a toast at the top tells it; a player the user opened shows its error instead. With `Config.matchFrameRate` (Appearance, Screen; TV only, off by default) the player switches the display to the mode that fits the frame rate of the video track (`DisplayModeMatcher`, `FrameRateSwitcher` through the window's `preferredDisplayModeId`; Media3 then asks the surface for nothing) and gives the mode back when it closes or the activity pauses. `NativePlayer` takes the audio focus (the sound of another app pauses it) and holds only the application context. Where the device has picture-in-picture (`PictureInPictureSupport.isAvailable`: `BuildConfig.PICTURE_IN_PICTURE`, Android 8+, `FEATURE_PICTURE_IN_PICTURE`, which many TVs and Google TV before 13 lack, and the app op not denied; else nothing offers it), a row of its menu and the PiP key of remotes (`KEYCODE_WINDOW`, which the system keeps while a PiP window is shown) put the video in a picture-in-picture window over the browser; only explicitly, never on Home (an app can not start an activity right after Home, and the TV quality guidelines ask for an explicit action). `PlayerScreenView.enterPictureInPicture` hands its playing `NativePlayer` to `PictureInPicturePlayback` (one per process, main thread) and takes a new one before it starts `PictureInPictureActivity` (`IncognitoPictureInPictureActivity` in `:incognito`; each a `singleTask` with a `taskAffinity` of its own and out of the recents), since the browser activity pauses then, which pauses the player of the screen. The browser activity itself never goes into PiP: it is the root of its task, so closing the window would finish it (and the incognito process). The window activity shows the same ExoPlayer and enters the window in its first `onResume` (the shape of the video within 2.38:1, the title on Android 13+, one `RemoteAction`, play or pause, a broadcast to a receiver of its own; its icon is a white bitmap, as the system can not resolve the theme attribute of the app's icon tint); the browser stays usable behind it. Closed (or stopped), it releases the player; expanded (it resumes out of the window) or Back while expanded, it starts the browser activity of its process with `MainActivity.KEY_SHOW_PIP_PLAYER`, whose shell takes the player back (`BrowserShell.showPictureInPicturePlayer`, `PlayerScreenView.adopt`: from where it is, without the intro), also in a new activity after its tabs load. A video opened in the built-in player ends the window, and the media keys of the remote go to the window while it floats over the browser (`MainActivity.commands`: the player, then the window, then the page); over other apps they reach it through `PlayerMediaSession`, a platform `MediaSession` that the window activity holds while it has the player (released when it gives the player back), which also tells the system the title (the notification of the window on Android TV 8 to 12 shows "No title program" without one; `setTitle` of the window parameters is for Android 13+).

**Home screen channels.** On Android TV 8+ (`HomeChannels.isSupported`: a TvProvider; the settings show them only there and in the TV interface) the app can publish three preview channels of `TvContract` (`channels` package), each off by default (Settings, Search and home page, Android TV home screen): the bookmarks (`Config.channelBookmarksSource`: those of the home page, those right in one folder (`channelBookmarksFolder`, the top level too) or all of them, as `FavoritesRepository.channelBookmarks` gives them), the open tabs (16:9 posters cut from their thumbnail files; none while incognito mode is on) and the finished downloads. `HomeChannels.sync` makes the channels of the given kinds what the settings say: an enabled one is created (`requestChannelBrowsable`; turning one on in the settings asks the system dialog when it is not shown yet) and a disabled one deleted, found by `COLUMN_INTERNAL_PROVIDER_ID` (no ids in prefs, so cleared data or a race leaves nothing behind; duplicate channels and programs are deleted); `ChannelPublisher` writes only the programs that differ, and a weight (the launcher puts heavier programs first) follows the place in the list, so a program added at the end changes no other; downloads, whose new ones come first, weigh their id. Syncs run one at a time in all processes (a mutex and a `FileLock` on `channels.lock`). They run when `MainActivity` stops (after `tabWrites`, so the thumbnails are written), when a setting changes, and in `:downloads` when a download is done (`Mode.UPDATE_EXISTING`: its prefs may be stale, so it only refreshes a channel that is there). Posters are drawn by the app (`ChannelPosters`, in `noBackupFilesDir` like the secret of the links: the posters of tabs show the open pages; favicons only from the app's cache, no network; a file named by a hash of what it shows, since the launcher keeps images by uri) and served by the exported `ChannelPostersProvider` to the app and system apps only. A bookmark tile shows a tab with its url if there is one (`MainActivity.channelBookmarkIntent`), a tab tile switches to its tab (`channelTabIntent`), a download tile goes to `ChannelLaunchActivity`, which checks the HMAC token of the link (a secret file of the app) and opens the file as OK on its row does, else the downloads screen. The provider and that activity run in `:downloads`, so the launcher does not start the browser.

**Settings.** What the settings screens show and do is in `SettingsNavigator` (no views): six categories (Search and home page, Sites, Appearance, Remote and cursor, which only the TV interface has, Advanced, About), each a list of `Section`s of `Row`s (a `Choice`, `segmented` for 2 or 3 short options and else opened as a menu of options, a `Toggle`, a `Slider`, a `Field` of text with an optional button, an `Action`, the key of a `ShortcutKey`, a `Link`, a `Notice`, `Info`). A row that depends on another setting is there only while it applies (the folder of downloads only where there is a picker of folders or one is chosen, the address of a custom search engine, the address of its suggestions while Search suggestions is on (a `Field` with the button Detect: `OpenSearchDetector` reads it from the OpenSearch description of the site, which a `<link rel="search">` of its start page or of a page of its search results points to, else `/opensearch.xml`; a site of an engine of the list gets the address of that engine), the User-Agent string while Custom is chosen, the links or the address of the home page, the filter lists while ads are blocked, the update channel and a new version while updates are checked); the darkening of pages and the tracking protection only where the engine supports them, the updates only in the generic build, the frame rate, the player of videos and the hint about found videos only in the TV interface. Settings that are read when the app starts (interface, theme, darkening, engine debugging) are marked After restart, and the screens offer Restart now while one differs from the value the process started with (`AppSettingsStore.rememberStartupValues`, called in `MainActivity.onCreate`), so nothing exits the app by itself. The navigator reaches the settings through its `Store` (`AppSettingsStore`: `Config`, `SettingsModel`, the ad block and update models; it makes the checks of the engine and the build, and writes through the paths that apply a setting: `SettingsModel.keepScreenOn`, `config.theme`, `setSearchEngineURL`, `BrowserController.onDefaultSiteViewChanged`); `SettingsShellCallback` gives both shells the dialogs (turning engine debugging on asks first), the key capture (`ShortcutKeyDialog`, an AlertDialog with its own window, so keys do not reach the shortcuts of the activity; the navigation keys still move its focus), links in a new tab, the update dialog and the restart. Texts typed in fields are saved when the field loses the focus, on Done and when the screen closes. The TV shell shows `SettingsScreenView` over the window (Settings in the ⋮ menu of the bar): the categories on the left (the focused one is shown), its card on the right, its menus in the `PopupMenuView` of the shell (`Item.checked` marks the chosen option). The phone shell shows `PhoneSettingsView` (the list of categories, then the page of one; menus in the `PhoneActionsSheet`). Both draw the rows with `SettingsRowsView`, which keeps the view of each row by its id, so the focus stays when rows appear or go; the phone page lays `ThemeOverlay.TVBro.Settings.Phone` over it, which gives the `tbSettings…` size attributes their phone values (the TV ones are in `Theme.TVBro`). Switches, sliders and segments are drawn with `ds_switch_*`, `ds_slider_*` and `ds_settings_segment_bg`; there is no segmented button library. About lists the libraries and resources of other authors the app ships (Third-party components, `ThirdPartyNotices`): each module keeps their notices in its own `assets/notices/<module>.json` (`app.json`, `gecko.json` of the gecko module, so only the GeckoView app lists GeckoView and what it brings, with no check of the engine), the full texts of the licenses are in `app/src/main/assets/notices/licenses`, and a row shows its notice and license in a dialog (`SettingsShellCallback.showNotice`, a focusable `ScrollView`, so the D-pad scrolls the text). A new dependency of the runtime classpath (also one that comes with another) gets a notice there.

**History.** `VisitedHistoryLogger` saves a visit (`onVisited` of the engine) after a few seconds, dropping the quick ones (redirects). A visit gets only a title received for its own url: engines report the visit when the page commits, before its title, and pages that change their url themselves (`history.pushState`) start no load, so `BrowserController` matches titles with the url of the engine (`webEngine.url`), not `tab.url`. What the history screens show and do is in `HistoryNavigator` (no views): the whole history is loaded when a screen opens (`HistoryRepository.all()`) and searched in memory (each word of the query in the title or the url, ignoring case also outside ASCII, which SQLite's LIKE does not fold), the options of a row, the selection mode (a long press) with Select all and Delete, Clear all. The TV shell shows `HistoryScreenView` over the window (History in the ⋮ menu of the bar), the phone shell `PhoneHistoryView` (its search field takes the place of the title); rows are bound by `HistoryRowBinder`, which marks the words found. Visits older than `Config.historyRetention` (Settings, Advanced, History: a week to a year, a year by default; there is no option to keep them forever, since the history is searched in memory, and nothing limits their number) are deleted by `HistoryRepository.trim`: when the tabs load, then once a day when a visit comes (`BrowserController.trimHistoryDaily`), and at once when the setting changes (`AppSettingsStore`).

**Favicons.** `FaviconsPool` (in `:app:common`) gives the icon of a host: from memory, from its file in the cache dir (`favicons/`, named in `HostConfig.favicon`), else from the network, where `FaviconExtractor` reads the `<link>`s of the page's head and its web manifest (`/favicon.ico` is always the last candidate) and `FaviconExtractor.rank` orders them for `TARGET_SIZE`: the smallest at least that big, then the biggest from `MIN_SHARP_SIZE`, then those of unknown size, then the small ones; SVG is skipped (BitmapFactory can not decode it). Up to a few are downloaded until one is sharp enough; icons are kept at most `MAX_STORED_SIZE`. One load per host runs at a time in the pool's own scope (callers only wait, so a recycled row cancels nothing), at most a few fetch at once, and a host whose page gave none is not asked again for 10 minutes. The icon a web engine reports (WebView's `onReceivedIcon`, mostly 16–32 px) is only provisional: `onEngineIcon` shows it at once (`get` gives it, the tab is updated), looks at the page and keeps the bigger one. A saved icon below `MIN_SHARP_SIZE` whose file is older than a week is looked up again in the background (a failed look touches the file); the UI shows the new one when it asks again. Nothing is written while incognito mode is on. The app's requests here have timeouts, a browser User-Agent and follow redirects from http to https (`FaviconExtractor.open`).

**Sending to the TV.** Any device sends addresses, searches and files to a TV through a web page, in any browser (`send` package, in `:app`); TV Bro on the phone is not needed. The TV screen `TvSendScreenView` (Send to this TV in the ⋮ menu of the bar, with the icon `ic_devices`: any device can send, not only a phone) shows the QR code of `https://tvbro.phlox.dev/send/#<inbox>` and a short address `tvbro.phlox.dev/c/<code>` to type (`SendLinks`: the inbox is 128 random bits kept in the prefs until New link, the code 8 characters of Crockford's base32, made while the screen is open and every 10 minutes). The page is `public/send` of the `tv-bro-web` repository (plain JS, its strings in `i18n.js` in the languages of the app), never under `/sync`: 3.0 betas open those links in the app. `SendSession` (main thread) waits only while the screen is open (it stops when the screen closes, also when a sent page opens, and when the activity stops): the free plan of the database takes 100 connections at once for all TVs; a file that is coming still comes whole (`LocalSendServer.stopListening`). Receiving is TV only (the user's choice): the phone UI has no screen of sending. Texts go through the Realtime Database of Firebase (`tv-bro-3546c`, its rules in `database.rules.json` of `tv-bro-web`) by its REST API, with no Firebase library: `CloudInbox` writes the info of the TV (`/inbox/<inbox>/info`: its name, its addresses in the local network, the key of its page there and until when it listens: 3 minutes ahead, written again every minute, so a TV whose process died stops taking messages soon; deleted with its code when the TV stops, so the database keeps nothing of TVs that do not listen); what a TV whose process died leaves (an expired info, its messages, an expired code) is deleted by `tools/clean-database.mjs` of `tv-bro-web`, run by hand with the Firebase CLI (its queries need the `.indexOn` of `exp` in the rules) and the codes (`/codes/<code>`), and listens to `/inbox/<inbox>/msgs` with server-sent events (`SseReader`; connections through `AppProxy.open`); the page writes messages there with `fetch`, which the rules take only while the info says the TV listens; the TV opens each one once and deletes it (those written before it listened only when fresh, by the clock of the server from the Date of its answers). A text opens as if typed into the address bar (`SendRules.urlOf`: `UrlInputResolver`, http and https only) in a new tab, or the tab of the same url (`TvShell.openSentText`; texts that come before the tabs are loaded wait). Files go only in the local network: browsers block requests of the https page to `http://192.168.…` as mixed content (Chrome lets it ask after the user allows the local network), so the TV serves a page of its own, `LocalSendServer` (plain HTTP/1.1 on the port of `SendSettings`, `assets/pages/send` filled with the strings of the TV by `LocalSendPage`), which the page of the site opens as a link (`http://<address>:<port>/#k=<key>`; in Chromium 142+ it first asks `/ping`, which answers the origins of the site); its requests need the key (`X-TVBro-Key`): texts (`POST /text`, as from the cloud, so the network works without Firebase) and files (`PUT /file`, the raw bytes with Content-Length). The traffic of that page is not encrypted. `SentFileReceiver` saves files as downloads: `DownloadLauncher.receive` inserts the row (url `tvbro-phone:<device>`, the browser and system the page tells, so it is not downloaded again and its caption shows the device; not resumable) and gives the write end of the reliable pipe of `StreamDownloadTask`, which the server fills (`closeWithError` when the file did not come whole, so the service drops it); the server answers when the row ends. The storage permission of Android 10 and older is asked for and the page told to send again. The phone sync of 3.0 betas (pairing, tabs and bookmarks both ways) is gone: `MIGRATION_28_29` drops its table and `LegacySync` its key and prefs. Debug builds log the link of the TV (`SendSession`).

**Global singletons.** `AppContext.get()` and `AppContext.provideConfig()` (initialized in `TVBro.onCreate`) give `:app:common` code access to the Application and the `Config` SharedPreferences wrapper. The Room database (`AppDatabase`, its schema version and hand-written migrations are in `singleton/AppDatabase.kt`) is opened by `AppContainer.database`; the app and the UI reach the data only through the repositories of `AppContainer.data` (`data` package: tabs, history, favorites, downloads, host configs), never through DAOs. `TVBro.container` (`AppContainer`; code that only needs a `Context` uses `AppContext.get()`, not the `TVBro` instance) also holds the application-wide `appScope` and `tabWrites`, a `SerialWriteQueue` through which all tab database and file writes go: they run one by one and are not cancelled with the activity or the model. Code that exits the process (`exitProcess`) waits for `tabWrites.awaitPending()` first, asynchronously; to exit (and optionally restart) when `MainActivity` finishes, call `TVBro.exitProcessAfterMainActivityFinish`.

**Flavors.** `BUILT_IN_AUTO_UPDATE` (a BuildConfig field) is true only for `generic`. `PICTURE_IN_PICTURE` (a BuildConfig field and the manifest placeholder `pictureInPicture` of the `supportsPictureInPicture` of the window activities, both set by `pictureInPicture()` in `app/build.gradle.kts`) is false only for `google`: the quality guidelines of TV apps on Google Play allow no media playback in picture-in-picture. The auto-updater reads `latest_version.json` from the repo (release/beta channels with per-ABI APK URLs). The two apps update only from their own APKs (`UpdateChecker`, keyed by `BuildConfig.FLAVOR_webengine`): `url`/`urls`/`minAPI` of a channel are the WebView app's (versions older than the split read only them, and they have its applicationId), the GeckoView app takes them from `variants.geckoIncluded` of the channel and gets no update from a channel without it. `foss` adds the `.foss` applicationId suffix. `geckoIncluded` adds the `.gecko` suffix (after the one of `appstore`: `com.phlox.tvwebbrowser.foss.gecko`), raises minSdk to 26 and adds the gecko module. The WebView engine is in the main source set, so it is compiled into both variants, but only `geckoExcluded` uses it.

**Home page.** `about:home` (`Config.HOME_URL_ALIAS`) is resolved by `HomePageUrl` in the core according to the home page mode; the built-in home page is `Config.HOME_PAGE_URL`. The page itself is in `app/src/main/assets/pages/home` (`index.html` and `index.js`, no inline scripts or handlers), and both engines show it from the APK: WebView serves it in `shouldInterceptRequest` under `Config.HOME_PAGE_URL`. GeckoView cannot serve local files that way, so the build of the gecko module copies the page into the bundled extension (`assets/extensions/generic/home`, a generated assets directory) and GeckoView shows it as a page of the extension (`moz-extension://…/home/index.html`). `GeckoWebEngine` hides that: it loads the local page for `Config.HOME_PAGE_URL` (waiting for the extension at startup), reports it back as `Config.HOME_PAGE_URL`, and replaces the web version (old links, saved tabs) with it. The page talks to the app through the `TVBro` object: added by WebView's `AndroidJSInterface`, or defined by `index.js` over the extension port (`AppHomePagePortDelegate`; the app calls the page through the port too, since extension pages run no `javascript:` urls). The extension is installed again when the hash of its files (`BuildConfig.WEB_EXTENSION_HASH` of the gecko module) changes. The web copy at tvbro.phlox.dev (the `tv-bro-web` repository) is only for older versions of the app.

**Error pages.** The certificate warning of WebView (`app/src/main/assets/pages/warning-certificate.html`) and the load error page of both engines (`app/common/src/main/assets/pages/error.html`) are HTML templates drawn with the tokens of the design system (light and dark through `prefers-color-scheme`, a phone layout under 600px). The engine fills their `{{name}}` holes with `ErrorPageTemplate.fill` (escaped values: localized strings of `:app:common`, the host, the error) before loading them, so they need no bridge to show the error; only "Continue" of the certificate warning calls `TVBro.reloadWithSslTrust()`. `LoadErrorPage.create` fills the load error page for a `LoadErrorKind` (insecure, dangerous, crashed, network, generic: the state of the page, which picks its glyph and buttons); each engine maps its errors to it (`GeckoLoadErrors`, `WebViewLoadErrors`). GeckoView gets the page as a base64 `data:` url from `onLoadError`. WebView has no way to restyle its own error page: `WebViewEx.onReceivedError` (main frame only, not for the certificate warning) keeps the page, and when WebView's error page finishes loading the page is written over it with `document.write` (`WebViewLoadErrors.replaceDocumentScript`), which adds no history entry; the script of the page is in a function (the globals of WebView's page stay) and sets `TVBRO_errorPage`, and when that is not set the page is loaded with `loadDataWithBaseURL` instead. Safe Browsing of WebView is always on (not tied to ad blocking); a hit of the main frame (`onSafeBrowsingHit`) is answered with `backToSafety`, so the load fails with `ERROR_UNSAFE_RESOURCE` and the page of a dangerous site shows the threat type. When the renderer of WebView dies (`onRenderProcessGone`, which returns true: false ends the app), each engine drops its view; the current tab tells the core (`TabEngineEvents.onEngineViewLost`), which attaches a new view, and the engine shows the crashed page for the lost url in it (Reload loads it again); a background tab gets a new view, restored from its saved state, when it is shown. When the content process of a GeckoView session crashes or is killed for memory (`MyContentDelegate.onCrash`/`onKill`), `GeckoWebEngine.onContentProcessLost` opens the session shown in the view again and gives it to the view anew (`releaseSession`, `setSession`: the view keeps the display of the closed session, so a session only opened again drew nothing and the page stayed covered in white), then restores its page; a background session stays closed until its tab is attached again (`onAttachToWindow` opens and restores it). The death of the GPU process of GeckoView alone needs nothing: Gecko starts another one and draws again. A screenshot of GeckoView (`GeckoViewEx.renderThumbnail`) waits at most a second, since Gecko does not answer while it draws nothing (the TV bar shows only once the picture is taken).

**Look.** Colors come from theme tokens: `?attr/tbColor…` attributes (`values/attrs.xml`) that `Theme.TVBro` maps to the semantic palette in `values/colors.xml` (night values in `values-night`). Layouts and drawables use the attributes, never hex colors or palette colors directly; code uses `Context.themeColor(R.attr…)`. Attributes need a themed (activity) context: do not inflate such views or drawables with the application context. A theme attribute does not resolve in `android:drawable` of a selector item (the drawable fails to load): put the color in a `<color>` or `<shape>` element inside the item. `ThemeResourcesTest` loads every drawable and color of the app with the app theme. The redesigned screens (the TV bar, the phone UI) use the tokens of the "TV Bro" design system instead: `?attr/tbColorDs…` attributes named as in its `tokens.json` (mapped to `ds_…` palette colors, night values in `values-night`; `tbColorDsDanger` is only for the glyphs of an insecure connection, never a fill), `ds_…` dimens, the `Widget.TVBro.Text.Address`/`Toast`/`MenuItem`/`TabTitle`/`CountBadge` styles and the `ds_…` state drawables (focused also when hovered by the cursor, selected when activated or selected). The overlays of the players over a video (the seek bar of the video mode, the built-in player with its panels and its error, the choice of a stream) always take the dark tokens: `ThemeOverlay.TVBro.Video`, set with `android:theme` on their views in `activity_main.xml`, maps the tokens that differ to the `ds_dark_…` palette, which `values-night` takes too, and their own `tbColorDsVideo…` colors (the dims, the gradient under the seek bar, the ring of the spinner) are the same in both themes (`VideoThemeTest`). The context of such a view is a `ContextThemeWrapper`, not the activity: unwrap it where the activity is needed. The other screens keep the older `tbColor…` palette until they are redesigned. Widgets get their look from styles in `values/styles.xml`, set with `style="..."` on each view: `Widget.TVBro.Button`/`Widget.TVBro.ImageButton` (the app button background; `.Ds.Segment`, `.Ds.Standalone` and `.Ds.Field` are the buttons of the redesigned bar, `.Ds.CursorMenu` the round buttons on the plate of the cursor menu) and `Widget.TVBro.Text.*` for text sizes (`Headline`, `Title`, `Subtitle`, `Body`, `Caption`, `Badge`; sizes in `values/dimens.xml`). These text styles set only `textSize`: a `textAppearance` would replace the default text color of the view. The theme sets no widget defaults (`buttonStyle` and others), so a view without a style keeps the platform look. Alert dialogs are the exception: `Theme.TVBro` sets `alertDialogTheme` to `ThemeOverlay.TVBro.Dialog.Alert` (the `ds_dialog_bg` window, ink text, `Widget.TVBro.DialogButton` buttons, `ds_menu_row_bg` list rows), so dialogs use `androidx.appcompat.app.AlertDialog` (in the gecko module too), never `android.app.AlertDialog` or `ProgressDialog`, which ignore it; `DialogThemeTest` checks the day and night looks. Repeated spacing values are dimens (`settings_content_padding`, `list_item_padding_*`). Icons are one vector per glyph with a role name (`ic_back`, `ic_close`, `ic_favorites`…): white paths and `android:tint="@color/icon_tint"`, which gives the icon color and the disabled one for a disabled view, so there are no per-color copies or selectors swapping images. A view that needs another color sets `app:tint` with a token (`tbColorIconSubtle` for the bookmark edit and delete buttons). An icon needed at another size in a `wrap_content` button gets a `layer-list` wrapper with the size, not a fixed view size: the button is then rounded to pixels like other icons of that size.

**Lists.** Lists are `RecyclerView`s with focusable rows (`Widget.TVBro.ListItem`: focusable, `list_item_bg_selector` background); there is no `ListView` left. The rows of the settings are the exception: they are a form (`SettingsRowsView`, see Settings), not a list. History and downloads are lists grouped by days (`widgets/datedlist`): `DatedListAdapter` (a `ListAdapter` that builds the header rows from the items, diffed in the background; act on the new rows in the `submitItems` callback), `StickyHeaderDecoration` (the pinned header of the top day with its shadow; items that are `isPinned` make a group of their own before the days, like the downloads in progress), `ListDividerDecoration` (its color and height can be given), and `StickyHeaderLayoutManager` (scrolls a focused row out from under the pinned header). They are in a `NearestFocusRecyclerView`: focus coming into the list from another view (`nextFocus...` set to the list) goes to the row nearest to that view, as in a ListView, and a focus request made while the layout is pending keeps the row that got it.

## Release

Releases use the manual `.github/workflows/release.yml` workflow (`workflow_dispatch` with a version). It needs the secret `QWANT_CLIENT_ID` (see Build & test). It builds per-ABI `genericGeckoIncluded` APKs (`-PenableAbiSplits`) and the `genericGeckoExcluded` release APK, renames them `tvbro-<version>-...apk`, and publishes a GitHub release whose body is `RELEASE_NOTES.md`. A version bump touches `versionCode`/`versionName` in `app/build.gradle.kts`, `latest_version.json`, `RELEASE_NOTES.md`, and the F-Droid/Play metadata changelog under `metadata/en-US/changelogs/<versionCode>.txt`. The app reads `latest_version.json` from `master` on GitHub, so changes to it go live once merged. In each channel, `url` is the `genericGeckoExcluded` APK, `minAPI` is 24 and there are no `urls` (an ABI match in them wins over `url`, so `genericGeckoIncluded` APKs there would be offered to the WebView app); `variants.geckoIncluded` holds `minAPI` 26 and the per-ABI `genericGeckoIncluded` APKs (`url`, `urls`); see Flavors.
