# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project

TV Bro is an Android web browser for TV remotes (D-pad navigation, virtual cursor, tabs, bookmarks, voice search, downloads, history), with a touch interface for phones in the same APK. It is built as two separate apps that differ in the engine rendering pages: the system WebView (applicationId `com.phlox.tvwebbrowser`) or a bundled GeckoView (`com.phlox.tvwebbrowser.gecko`). The engine of an app can not be changed.

## Build & test

Gradle (Kotlin DSL) with JDK 21. On Windows use `gradlew.bat` / `.\gradlew`.

Variants combine two flavor dimensions with the build type: `appstore` = `generic` | `google` | `foss`, and `webengine` = `geckoIncluded` (the GeckoView app) | `geckoExcluded` (the WebView app). Examples:

```bash
./gradlew assembleGenericGeckoIncludedDebug
```
```bash
./gradlew assembleGenericGeckoExcludedRelease
```
```bash
./gradlew testGenericGeckoIncludedDebugUnitTest
```
```bash
./gradlew :app:testGenericGeckoIncludedDebugUnitTest --tests "com.phlox.tvwebbrowser.utils.FaviconExtractorTest"
```
```bash
./gradlew :app:common:testDebugUnitTest
```

- Pass `-PenableAbiSplits` to `assemble` to produce per-ABI APKs (armeabi-v7a, arm64-v8a, x86_64).
- Release signing reads the env vars `KEYSTORE_PATH`, `KEYSTORE_PASSWORD`, `KEY_ALIAS` and `KEY_PASSWORD`. Without `KEYSTORE_PATH`, release builds are unsigned.
- App unit tests use Robolectric (`isIncludeAndroidResources = true`). There are no instrumented tests. Browser core tests use `FakeWebEngine` (registered through `WebEngineFactory.initializeForTests`) and an in-memory Room database (`AppDatabase.setInstanceForTests`).
- Room schemas are exported to `app/schemas` and committed. `AppDatabaseMigrationTest` builds databases of old versions from them, so a database version bump needs its schema exported (it is generated by the build) and a migration test.
- `buildSrc` compiles with `allWarningsAsErrors = true`.

## Module layout

- `:app`: the base application. It holds the browser core (`browser` package, see below), the UI (activities, dialogs, settings), the Room `AppDatabase`, the download service, the WebView engine (`webengine/webview`), adblock and auto-update.
- `:app:common`: an Android library shared by `:app` and `:app:gecko`. It holds the engine abstraction (`webengine/WebEngine.kt` and `WebEngineFactory`), the `Config` prefs, the Room entity models, `AppContext`, `ActiveModel`/`ActiveModelsRepository`, and the cursor widgets (`CursorLayout`, `CursorDrawerDelegate`). Code that both engines need belongs here, because the gecko module must not depend on app-only classes.
- `:app:gecko`: the GeckoView engine (`GeckoWebEngine`, delegates, and a bundled WebExtension under `assets/extensions/generic`). An Android library that `:app` depends on only in `geckoIncluded` variants (`geckoIncludedImplementation`); its keep rules for the app's R8 are in `consumer-rules.pro`.
- `buildSrc`: convention plugins `tvbro.android.application` and `tvbro.android.library` (both in `TvBroAndroidModulePlugin.kt`). They apply AGP and set compileSdk, minSdk and targetSdk from `gradle/libs.versions.toml`. The product flavors are declared in `app/build.gradle.kts`. All dependency versions live in that version catalog.

## Key architecture

**Web engine plug-in mechanism.** Each variant has one engine, chosen at build time: the `webengine` flavor sets `BuildConfig.WEB_ENGINE_CLASS` (`...GeckoWebEngine` in `geckoIncluded`, `...WebViewWebEngine` in `geckoExcluded`). Engines register themselves rather than being referenced directly. Each engine class has a `companion object { init { WebEngineFactory.registerProvider(...) } }`, and `TVBro.initWebEngineStuff()` triggers that registration with `Class.forName(BuildConfig.WEB_ENGINE_CLASS)`. `WebEngineFactory` holds that one provider (registering another one fails) and `initialize()`, called from `MainActivity`, initializes it. There is no engine setting and no switching at runtime. **Keep base-app code free of compile-time references to gecko classes.** All interaction goes through the `WebEngine` interface and `WebEngineFactory`. Common code must not check which engine is active either: engine-specific behavior goes through `WebEngineProviderCallback` hooks (incognito data isolation and cleanup, clearing the data of one site with `clearSiteData`/`supportsSiteDataClearing`, failure to create a view, `supportsSetting` for settings only some engines have, see `EngineSpecificSetting`) or `WebEngine` properties (for example `stateFilePrefix` of saved tab state files). `BrowserTab.webEngine` is created lazily; check `isWebEngineCreated` before touching the engines of all tabs. On devices without a hardware AV1 decoder (`HardwareCodecs`) GeckoView turns AV1 off when its runtime starts (`media.av1.enabled` on the default branch, so it is not kept): sites such as YouTube would serve AV1 to it and its software decoder (dav1d) can not keep up on TV chips; WebView already chooses VP9 there.

**Virtual cursor.** The cursor is an optional engine capability: an engine that supports it implements `VirtualCursorSupport` (cursor vs. direct navigation mode, the `CursorDrawerDelegate`), and the UI reaches it only through `webEngine.virtualCursor`. Each engine owns its cursor surface: the WebView engine wraps every `WebViewEx` (and its fullscreen view) in its own `CursorLayout`, Gecko draws the cursor on `GeckoViewWithVirtualCursor` (one view shared by all tabs). The activity's tabs container (`flWebViewContainer`) is a plain `FrameLayout`. When another tab is shown, `MainActivity.onRenderedTabChanged` turns the grab and direct navigation modes off. `CursorDrawerDelegate` (keys, movement, press and grab state) leaves the work to the classes next to it: `CursorRenderer` draws, a `PointerEmulator` talks to the page, `CursorScroller` scrolls at the edges (the engine's `customScrollCallback`, then the "scroll hack", a touch drag) and `PinchZoomGesture` zooms. The emulator is a finger (`TouchEmulator`) or a mouse (`MouseEmulator`: hover, primary button press and release with the `ACTION_BUTTON_PRESS`/`RELEASE` events WebView needs, wheel scrolling of the element under the cursor), chosen by `CursorDrawerDelegate.pointerMode`; the engines set the mouse for pages in the desktop view (`SiteViewSupport.desktopView`). The cursor surface is a `PointerTarget` (`CursorLayout`, `GeckoViewWithVirtualCursor`): synthetic hover and wheel events skip its D-pad adapter, and it gives the pixels of one wheel click of its engine. Switching the mode or turning the cursor off cancels the press and the hover in flight. A mouse cannot cancel a press (its release is a click, GeckoView keeps the element `:active`), so its press waits until the cursor moves (a drag, pressed where the key went down) or the key goes up (a click), and a long press, which opens the cursor menu, leaves nothing in the page; the mouse hovers the point when the key goes down, so WebView's long press script (`TVBRO_activeElement`, also set by `mousemove` in `generic_injects.js`) finds the link. GeckoView learns the element under a mouse only from its context menu, so its surface asks for a right click on a long press (`PointerTarget.contextClickOnLongPress`, which brings `ContentDelegate.onContextMenu`). GeckoView treats mouse presses as touches on devices in the television UI mode (`PanZoomController.treatMouseAsTouch`, a static flag also used for physical mice); `GeckoViewWithVirtualCursor` turns it off by reflection only while it dispatches a press of the cursor's mouse (kept in `consumer-rules.pro`). GeckoView opens no soft keyboard for a field a mouse clicks, so `MyTextInputDelegate` (around its default text input delegate) asks for it after a click of the cursor (`onCursorMouseClick`) that focused a field or went into the focused one, hiding it first: a show request made before the keyboard started the input of the field fails and makes the window drop the next ones.

**Site view and site settings.** Showing a site as on a desktop computer or as on a phone is an engine capability too: an engine implements `SiteViewSupport` (`desktopView`: a desktop User-Agent and a wide viewport; WebView builds them in `DesktopView` from the system User-Agent, GeckoView switches its User-Agent and viewport modes), reached through `webEngine.siteView`. The view is kept per host (`HostConfig.desktopView`, null follows the default; like ad blocking, `HostConfigRepository` keeps these settings of all hosts in memory, loaded before the tabs, so engines ask synchronously). The default is `Config.defaultDesktopView` (Settings: Default site view), null following the interface: `BrowserController.interfaceDesktopView`, set by `MainActivity`, desktop on TV and mobile on phones. The core sets the view before it loads a url or restores a tab; for navigations of the page to another host engines ask `EnginePolicies.isDesktopView` (WebView starts the navigation again, GeckoView changes the session settings before the load goes on and starts redirects again, once); a page that still starts in the view of another host loads again once (`onPageStarted`). There is no User-Agent setting: `WebEngine.userAgentString` only tells the current one (for downloads). `CurrentTabState.connection` (`SiteConnection`: no site, secure, http, certificate error; a certificate error stays with its host until the user navigates or the tab shows another host) gives the site button its sliders or the warning sign in `tbColorDsDanger` (`showSiteConnection`), and the header of the site settings its connection line. The built-in home page has no site. The site settings are one view, `SiteSettingsView`, in three variants (`siteSettingsVariant`): the TV `SitePanelView` under the site button, the phone `PhoneSiteSheet` (from the site button of the pill or the site header of the menu sheet) and the site section of the `PhoneMenuSheet` (rows without icons, no Clear site data). Its rows call `BrowserShell.Host` (`toggleSiteAdBlock`, `choosePopupBlockLevel`, `chooseSiteView`, `clearSiteData`, the dialogs are in `MainActivity`); the page reloads and the panel or sheet stays open. Clear site data asks first and removes the cookies, stored data and cache of the site (`BrowserController.clearSiteData`), not its settings and history.

**Shells: the TV and the phone UI.** `MainActivity` does what both looks share (the browser core, intents, navigation, incognito, downloads, keys and Back) and leaves the look to a `BrowserShell`, which it creates in `onCreate`: `TvShell` (`activity_main.xml`: the bar of the redesign over the page, the virtual cursor) or `PhoneShell` (`activity_main_phone.xml`: touch only, the virtual cursor is turned off for every tab view, the bottom `PhoneBar`, which `ScrollAwayBar` slides away while the user scrolls the page down (touches are tracked by the tabs container, `TouchTrackingFrameLayout`), the `PhoneMenuSheet`, the `PhoneSiteSheet`, the `PhoneTabSwitcher`, the `PhoneBookmarksView`, the `PhoneDownloadsView` and the `PhoneSettingsView` over the window, the `PhoneSnackbar` over the page). The shell gets the activity as `BrowserShell.Host` and is told about the engine views, the current tab state, UI events, fullscreen and Back. `UiModeSelector` picks the shell from the Interface setting (`Config.interfaceMode`); on Auto, the phone UI is for devices that are not a TV, have no leanback feature, have a finger touch screen and are narrower than 600dp (no tablets for now). Changing the setting restarts the app. The activity is not recreated on rotation or size changes (`configChanges`), so the engine views stay; the phone window is drawn edge to edge and `PhoneShell` applies the insets. The phone settings have no Remote and cursor category (see Settings). The built-in home page has a layout for phones (a CSS media query in `assets/pages/home/index.html`; the copy on the website, used by GeckoView, has to be kept the same).

**Commands and Back.** Browser actions triggered by the user from anywhere (hotkeys of `ShortcutMgr`, voice search) go through `browser/BrowserCommands`, which the activity implements; the buttons of the TV bar call `BrowserController` from the shell. The media keys (play/pause, stop, rewind, fast forward) go to the engine, which runs `assets/media_controls.js` in every frame (players are mostly in iframes of other sites): WebView injects it (started by `webview_media.js`, reporting to `WebViewMediaControls`), GeckoView has it in the content script of its extension (the build copies it there, each frame reports through its own port); the script reports the media of its frame, `MediaFrames` picks the frame (the one with a fullscreen video, else the one that started playing last) and the command goes to that frame only (its reply proxy, its port). GeckoView falls back to its `MediaSession` when no frame reports media. Engines that implement `MediaPlaybackSupport` (`webEngine.mediaPlayback`; both do) also give the state of that media (`MediaState`: playing, position, duration, whether it is in the fullscreen view, from the reports of the script, `MediaReports`) and seek in it. The TV shell uses them for the video mode (`VideoModeController`, no views): while the page shows a video in fullscreen the cursor is hidden and the keys control the video (Left and Right seek, faster while held, to where the key goes up; OK plays and pauses; Up and Down give the cursor back, and Back with that cursor hides it again, its callback is above the fullscreen one), with the seek bar `VideoOsdView` (it shows for a while when the video mode starts, longer when it has the hint of the built-in player). The shell gets the keys first (`BrowserShell.dispatchKeyEvent`), and in fullscreen Back never reaches the engine views: the back callbacks decide. The videos of the page that other apps can play (`PageVideo`: a file a media element plays, or the manifest of an HLS or DASH stream, never `blob:` media) are found by `assets/page_videos.js` in every frame: the media elements and, through a `PerformanceObserver`, the `.m3u8` and `.mpd` files the page loads; WebView runs it with `media_controls.js`, GeckoView in the content script of its extension (the build copies it there), and engines that implement `PageVideosSupport` (`webEngine.pageVideosSupport`; both do) give them as a flow, the reports of the frames kept together by `PageVideoList` (one address once, the variants of an HLS stream not apart, cleared when the page changes). The TV bar has a Videos button with their number (dimmed without videos, as Back and Forward are); its `VideosPanelView` lists them, OK opens one in a player app chosen in the dialog of Android (`ExternalVideoPlayer`: the Referer of its frame, the User-Agent and the cookies of the engine, in `Browser.EXTRA_HEADERS` and the `headers` list of MX Player), its options also copy the address and download a file; the page keeps playing them as before. When one of them starts to play with sound in the page (`mediaVideo`; the script reports `muted` too, `MediaState.muted`), the TV shell shows a hint plate for a few seconds, `PageVideoHintView` at the top end where the Videos button is, also with the bar hidden; it takes no focus and no keys. Its rules are in `PageVideoHintController` (no views): it shows after the video has played for 3 s while nothing covers the page (the shell checks the bar, panels, menus, screens, the player and fullscreen on each redraw), never for short videos, at most once per page (the tab and its address without the fragment, kept in memory), and only while `Config.pageVideoHint` (Settings, Sites) is on and the user has opened the built-in player fewer than 3 times (`Config.builtInPlayerOpens`). Back while it shows (its callback is just above the one of the menu) opens the bar, then the Videos panel at the row of that video (`VideosPanelView.show` with `focusUrl`), so Back, OK plays it in the built-in player; the row of the video the page plays says "Playing on the page". Every Back (the BACK/ESCAPE key, the system back callback, the B button of game controllers) goes through `BackNavigationEventsAdapter`: it removes duplicates between these channels and handles the "long press B" mode of game controllers in the direct navigation mode. The adapter feeds `MainActivity.screenBackDispatcher`, an own `OnBackPressedDispatcher` of the screen: each overlay has an `OnBackPressedCallback` there that it enables while it is shown, registered in `onCreate` from the lowest priority (the menu) to the highest (the cursor modes, which come from `VirtualCursorSupport.cursorModes`). Voice input (`VoiceSearchHelper`; from Android 11 its own plate at the bottom center of the window, where toasts show, and its errors as toasts of the shell, `BrowserShell.showMessage`) is cancelled by Back: its callback is added after all the others. Never add overlay callbacks to the activity's `onBackPressedDispatcher`: it has one always enabled callback that goes to the adapter. When something else has already handled a Back press in progress (the fullscreen view of WebView leaves fullscreen on BACK down), call `consumeCurrentPress()`.

**Browser core and engine callbacks.** `browser/BrowserController` (an `ActiveModel`) owns the tabs: their list, the current tab, persistence, opening/closing/switching, navigation, the engine events and the browsing history. It knows nothing about views: an activity attaches itself as `BrowserController.TabViewHost`, which creates engine views (`createTabView`) and provides the UI part of the engine callbacks (`uiHost`). The engine of the current tab gets a `WebEngineCallbacks` in `onAttachToWindow`; it is composed of three parts, all in `webengine/WebEngineCallbacks.kt`: `TabEngineEvents` (implemented by the controller), `EnginePolicies` (`TabPolicies`: ads, dialogs and new windows blocking, the site view) and `EngineUiHost` (implemented by the activity: menus, dialogs, fullscreen, page scrolling, permissions and file picking with result callbacks, downloads as `DownloadRequest`). The callbacks are set only while the tab is current, so background tabs report nothing. The UI renders `BrowserController.currentTabState` (`StateFlow<CurrentTabState>`) and handles one-time `BrowserUiEvent`s from `uiEvents` (a channel with a single collector). Other core pieces: `HomePageLinks` (links of the built-in home page), `VisitedHistoryLogger`, `HomePageUrl` (resolves `about:home`, engines never get the alias), `UrlRouter`/`UrlInputResolver`/`PopupBlockPolicy`, `Downloads.kt`. Activities start other activities and ask for permissions through `utils/launchForResult` (the ActivityResult registry), never with request codes.

**State models.** Screens keep state in `ActiveModel` subclasses (for example `BrowserController`, `SettingsModel`, `AdblockModel` and `DownloadsModel`). They get them through `ActiveModelsRepository.get(Model::class, activity)`, not through AndroidX ViewModel. A model is released when every activity using it finishes. Older observable state uses the custom `utils/observable` types (`ObservableValue` and `ObservableList`); new code uses `StateFlow`/`Flow` (with immutable values: a `StateFlow` does not emit a value equal to the previous one).

**Tabs.** `BrowserTab` (in `:app:common`, engines get it) is a tab in memory: its engine, thumbnail and page state; it is read and changed on the main thread only. The database keeps `TabEntity` snapshots (`toEntity()`/`fromEntity()`), and `browser/TabFilesStore` keeps the files of tabs (engine states, WebP thumbnails), getting and returning file names without touching tabs. `BrowserController.saveTab` takes the snapshot when called and enqueues the write in `tabWrites`; the queue runs on the main thread, so the id and the file names given by earlier writes are applied there. A tab is saved when it stops or starts being the current one and when the activity pauses.

**Bookmarks.** `FavoriteItem`s are kept in folders: a folder is an item without a url, its contents point to it with `parent` (0 is the top level, `FavoritesRepository.ROOT`). The bookmarks of the built-in home page are the Home page folder (`FavoritesRepository.HOME_PAGE`, no row in the table: they are marked with `homePageBookmark`, hold no folders and are not in the top level). In a folder, folders come first, then bookmarks, each by `order` (the newest first among equal orders): new items go to the top, new home page bookmarks to the end. The home page shows the bookmarks of its folder in that order (a link's `order` is its place on the page) and leaves out those it has no room for; `HomePageLinks.load()` is called after bookmarks change. Use the repository (`add`, `moveTo`, `move`, `delete` with the contents of a folder), not the DAO. What the bookmarks screens show and do is in `BookmarksNavigator` (no views: a stack of screens, a folder, the form of a bookmark or folder, the choice of a folder, the search of all folders, the bookmarks files in Downloads and the ways to import one, rendered through its `Host`); the shells only draw it. Export and import use the HTML bookmarks file of Chrome, Firefox and Edge (`data/BookmarksHtml`, a pure reader and writer; the Home page folder is marked with `TVBRO_HOME_PAGE` on its H3); `FavoritesRepository.importBookmarks` holds the rules of the new folder and merge imports, and `DeviceBookmarkFiles` (the navigator's `Files`) saves to and lists Downloads as downloads do (MediaStore from Android 11, which lists only the app's own files there) and opens the system picker. The TV bar keeps Bookmarks, Downloads and Incognito as buttons; History, Phone sync and Settings are in the `PopupMenuView` of its ⋮ button (`TvShell.showMoreMenu`). The TV shell shows the bookmarks in `BookmarksPanelView`, under the star of the bar, with the row menus in a `PopupMenuView` (both are `AnchoredOverlayView`s, which keep the focus inside them while open). The phone shell shows it in `PhoneBookmarksView` over the whole window, with the actions of a row in a `PhoneActionsSheet` and reordering by dragging; the Bookmark button of the menu sheet adds the page, or opens its bookmark.

**Downloads.** `DownloadService` runs in its own process (`:downloads`, see the manifest), so downloads go on while the browser switches between its normal and `:incognito` processes (which kill each other) and both can start them; `TVBro.onCreate` initializes only the database and the notification channel there. The browser processes reach it through `AppContainer.downloadService` (`DownloadServiceClient`): `DownloadCommands` (start, cancel, pause, resume) in `Message`s of a `Messenger`, which wait until the service is bound; the screens keep it bound while they are started. Nothing comes back through the binder: the database is the only state. `DownloadLauncher` inserts the row of a new download (`Download.status`: in progress, paused, done, failed, cancelled; `error` keeps a reason, see `Download.Error`) before it sends the start; the service writes the progress every second and the end, and on its start makes the downloads a dead process left in progress paused (resumable) or failed. `AppDatabase` is opened with multi-instance invalidation, so the Room flows of the browser processes see these writes; `DownloadsModel` turns them into `DownloadItem` snapshots with speeds and `DownloadEvent`s (a download ended). Responses a web engine fetched itself (GeckoView) and blob data cannot cross processes: the launcher copies them into a reliable pipe whose read end goes with the start command (its own copy is closed without a status, see `DownloadServiceClient`); a cut pipe fails the download. `HttpDownloads` requests files (redirects followed by hand, cookies only to the host of the site, no content encoding); a download is resumable when the server gives byte ranges and its size: pause keeps the file (pending in MediaStore on Android 11+) and resume asks for the rest with Range and If-Range (`decideRange`). Cookies are never stored: resume and Download again take them from the engine of the current tab (`BrowserShell.Host.downloadCommands`). Incognito downloads keep no `referer` (the page they came from). What the downloads screens show and do is in `DownloadsNavigator` (no views; looks: the TV panel of the bar with the latest downloads, the TV screen and the phone page of all downloads with filters by `Kind`), its `Device` is `DeviceDownloads` (open, install, share, the Downloads folder through `DownloadFileActions`; Android TV sends intents no app handles to stubs that only show a toast, they count as none). The TV shell shows `DownloadsPanelView` under the Downloads button of the bar (with a badge of the active downloads) and `DownloadsScreenView` over the window; the phone shell shows `PhoneDownloadsView`; rows are bound by `bindDownloadRow`, captions made by `DownloadRowText`.

**Built-in player.** The TV shell plays the videos of pages (`PageVideo`) in a player of its own, on Media3 (ExoPlayer: HLS, DASH and files), because the engines draw video into the window (1080p on a 4K TV, at a high CPU cost in WebView) and the player gives it a `SurfaceView` layer of its own. It is a view over the whole window of the browser activity, `PlayerScreenView`, in the process of the page (normal or `:incognito`), not an activity. `player/NativePlayer` (no views) wraps ExoPlayer: it requests the video with the headers of the page (`ExternalVideoPlayer.headers`: the Referer of its frame, the User-Agent and the cookies of the engine) and tells its state as a flow. The keys are those of the video mode (a `VideoModeController` of its own, whose host takes Up and Down): Left and Right seek, OK plays and pauses, Up and Down (and the Menu key, which a Shield keeps to itself) open the menu of the quality, the audio track, the subtitles and the speed (`PlayerTracks`, in a `PopupMenuView` of the player); the media keys of the remote go to it while it is open (`BrowserShell.onMediaCommand`); Back closes the menu, then the player (its callback is the highest). OK on a row of the Videos panel opens it (the video the page plays goes on from where it is; its options keep the other app); in the video mode Down takes the fullscreen video of the page there, from where it is, when the engine knows its stream (`PageVideosSupport.mediaVideo`: `PageVideoMatch` of what `media_controls.js` reports the media plays and the videos of its frame; the seek bar shows the hint). The page pauses its media (`MediaPlaybackSupport.pausePlayback`) and leaves fullscreen when the player opens. An error offers the video to another app. With `Config.matchFrameRate` (Appearance, Screen; TV only, off by default) the player switches the display to the mode that fits the frame rate of the video track (`DisplayModeMatcher`, `FrameRateSwitcher` through the window's `preferredDisplayModeId`; Media3 then asks the surface for nothing) and gives the mode back when it closes or the activity pauses.

**Settings.** What the settings screens show and do is in `SettingsNavigator` (no views): six categories (Search and home page, Sites, Appearance, Remote and cursor, which only the TV interface has, Advanced, About), each a list of `Section`s of `Row`s (a `Choice`, `segmented` for 2 or 3 short options and else opened as a menu of options, a `Toggle`, a `Slider`, a `Field` of text with an optional button, an `Action`, the key of a `ShortcutKey`, a `Link`, `Info`). A row that depends on another setting is there only while it applies (the address of a custom search engine, the links or the address of the home page, the filter list while ads are blocked, the update channel and a new version while updates are checked); the darkening of pages only where the engine supports it, the updates only in the generic build, the frame rate and the hint about found videos only in the TV interface. Settings that are read when the app starts (interface, theme, darkening, engine debugging) are marked After restart, and the screens offer Restart now while one differs from the value the process started with (`AppSettingsStore.rememberStartupValues`, called in `MainActivity.onCreate`), so nothing exits the app by itself. The navigator reaches the settings through its `Store` (`AppSettingsStore`: `Config`, `SettingsModel`, the ad block and update models; it makes the checks of the engine and the build, and writes through the paths that apply a setting: `SettingsModel.keepScreenOn`, `config.theme`, `setSearchEngineURL`, `BrowserController.onDefaultSiteViewChanged`); `SettingsShellCallback` gives both shells the dialogs (turning engine debugging on asks first), the key capture (`ShortcutKeyDialog`, an AlertDialog with its own window, so keys do not reach the shortcuts of the activity; the navigation keys still move its focus), links in a new tab, the update dialog and the restart. Texts typed in fields are saved when the field loses the focus, on Done and when the screen closes. The TV shell shows `SettingsScreenView` over the window (Settings in the ⋮ menu of the bar): the categories on the left (the focused one is shown), its card on the right, its menus in the `PopupMenuView` of the shell (`Item.checked` marks the chosen option). The phone shell shows `PhoneSettingsView` (the list of categories, then the page of one; menus in the `PhoneActionsSheet`). Both draw the rows with `SettingsRowsView`, which keeps the view of each row by its id, so the focus stays when rows appear or go; the phone page lays `ThemeOverlay.TVBro.Settings.Phone` over it, which gives the `tbSettings…` size attributes their phone values (the TV ones are in `Theme.TVBro`). Switches, sliders and segments are drawn with `ds_switch_*`, `ds_slider_*` and `ds_settings_segment_bg`; there is no segmented button library.

**History.** `VisitedHistoryLogger` saves a visit (`onVisited` of the engine) after a few seconds, dropping the quick ones (redirects). A visit gets only a title received for its own url: engines report the visit when the page commits, before its title, and pages that change their url themselves (`history.pushState`) start no load, so `BrowserController` matches titles with the url of the engine (`webEngine.url`), not `tab.url`. What the history screens show and do is in `HistoryNavigator` (no views): the whole history is loaded when a screen opens (`HistoryRepository.all()`, `trim` keeps it small) and searched in memory (each word of the query in the title or the url, ignoring case also outside ASCII, which SQLite's LIKE does not fold), the options of a row, the selection mode (a long press) with Select all and Delete, Clear all. The TV shell shows `HistoryScreenView` over the window (History in the ⋮ menu of the bar), the phone shell `PhoneHistoryView` (its search field takes the place of the title); rows are bound by `HistoryRowBinder`, which marks the words found.

**Sync of a phone with a TV.** A phone sends tabs and bookmarks to a paired TV over the local network (`sync` package, in `:app`, the same in both apps, so a phone of one app pairs with a TV of the other). The TV shell runs a `SyncServer` while the activity is started (on the same port each time if it is free, advertised with NSD by `SyncDiscovery`); the phone is only a client (`SyncClient`). Pairing: the TV screen `TvSyncScreenView` (Phone sync in the ⋮ menu of the bar) shows the QR code of a `SyncLink` (`https://tvbro.phlox.dev/sync#…`: the addresses and port of the TV and a one-time secret in the fragment); the camera opens it in the app (the App Link filter of `MainActivity`, verified by `public/.well-known/assetlinks.json` of the `tv-bro-web` repository, which lists the four packages and their signing keys), or else the page `public/sync/index.html` of the site opens there and hands the link to the app as `tvbro://sync#…`; `MainActivity` gives it to `BrowserShell.handleSyncLink`, and a link that was used already is ignored (Android gives a recreated activity its first intent again). `SyncChannel` is the encrypted channel: a handshake in the clear (nonces, the pairing id), then JSON frames sealed with AES-GCM by keys derived with HKDF from the shared key (the secret of the QR code, then the pairing key the TV gives). Both sides keep the pairing in `paired_devices` (`PairedDevicesRepository`; the key is wrapped by a key of the Android keystore, `SyncKeyStore`, so restored backups do not carry it). Requests (`SyncRequests`): open tabs (http and https only), get all bookmarks, preview and replace bookmarks, forget. Bookmarks go both ways as a `SyncBookmark` tree of what the user chose (`BookmarkSelection`, from the bookmarks of the phone, or from the tree the TV gives for the phone to take): `BookmarksReplacer` makes a folder chosen in full the same on the device that gets it and only adds to a folder chosen in part. `LocalBookmarks` does it for both sides (the TV for a phone, the phone for bookmarks it takes): in one transaction, after a dry run that the phone showed to the user (refused if it would now change something else), keeping the bookmarks of before in a `BookmarksBackup` for Undo (on the TV screen of the pairing, and on the screen of a TV on the phone). The phone page is `PhoneSyncView` drawing `PhoneSyncNavigator` (Send to TV in the menu sheet); it asks for the local network permission first. Debug builds log the pairing link of the TV (`SyncServer`), which can be opened on a phone with `adb shell am start -a android.intent.action.VIEW -d '<link>'` when no camera can scan it; `-PdebugApplicationIdSuffix=.dev` installs a debug build next to a release one.

**Global singletons.** `AppContext.get()` and `AppContext.provideConfig()` (initialized in `TVBro.onCreate`) give `:app:common` code access to the Application and the `Config` SharedPreferences wrapper. The Room database (`AppDatabase`, its schema version and hand-written migrations are in `singleton/AppDatabase.kt`) is opened by `AppContainer.database`; the app and the UI reach the data only through the repositories of `AppContainer.data` (`data` package: tabs, history, favorites, downloads, host configs), never through DAOs. `TVBro.container` (`AppContainer`; code that only needs a `Context` uses `AppContext.get()`, not the `TVBro` instance) also holds the application-wide `appScope` and `tabWrites`, a `SerialWriteQueue` through which all tab database and file writes go: they run one by one and are not cancelled with the activity or the model. Code that exits the process (`exitProcess`) waits for `tabWrites.awaitPending()` first, asynchronously; to exit (and optionally restart) when `MainActivity` finishes, call `TVBro.exitProcessAfterMainActivityFinish`.

**Flavors.** `BUILT_IN_AUTO_UPDATE` (a BuildConfig field) is true only for `generic`. The auto-updater reads `latest_version.json` from the repo (release/beta channels with per-ABI APK URLs). The two apps update only from their own APKs (`UpdateChecker`, keyed by `BuildConfig.FLAVOR_webengine`): `url`/`urls`/`minAPI` of a channel are the WebView app's (versions older than the split read only them, and they have its applicationId), the GeckoView app takes them from `variants.geckoIncluded` of the channel and gets no update from a channel without it. `foss` adds the `.foss` applicationId suffix. `geckoIncluded` adds the `.gecko` suffix (after the one of `appstore`: `com.phlox.tvwebbrowser.foss.gecko`), raises minSdk to 26 and adds the gecko module. The WebView engine is in the main source set, so it is compiled into both variants, but only `geckoExcluded` uses it.

**Home page.** `about:home` (`Config.HOME_URL_ALIAS`) is resolved by `HomePageUrl` in the core according to the home page mode; the built-in home page is `Config.HOME_PAGE_URL`. The page itself is in `app/src/main/assets/pages/home` (`index.html` and `index.js`, no inline scripts or handlers), and both engines show it from the APK: WebView serves it in `shouldInterceptRequest` under `Config.HOME_PAGE_URL`. GeckoView cannot serve local files that way, so the build of the gecko module copies the page into the bundled extension (`assets/extensions/generic/home`, a generated assets directory) and GeckoView shows it as a page of the extension (`moz-extension://…/home/index.html`). `GeckoWebEngine` hides that: it loads the local page for `Config.HOME_PAGE_URL` (waiting for the extension at startup), reports it back as `Config.HOME_PAGE_URL`, and replaces the web version (old links, saved tabs) with it. The page talks to the app through the `TVBro` object: added by WebView's `AndroidJSInterface`, or defined by `index.js` over the extension port (`AppHomePagePortDelegate`; the app calls the page through the port too, since extension pages run no `javascript:` urls). The extension is installed again when the hash of its files (`BuildConfig.WEB_EXTENSION_HASH` of the gecko module) changes. The web copy at tvbro.phlox.dev (the `tv-bro-web` repository) is only for older versions of the app.

**Error pages.** The certificate warning of WebView (`app/src/main/assets/pages/warning-certificate.html`) and the load error page of both engines (`app/common/src/main/assets/pages/error.html`) are HTML templates drawn with the tokens of the design system (light and dark through `prefers-color-scheme`, a phone layout under 600px). The engine fills their `{{name}}` holes with `ErrorPageTemplate.fill` (escaped values: localized strings of `:app:common`, the host, the error) before loading them, so they need no bridge to show the error; only "Continue" of the certificate warning calls `TVBro.reloadWithSslTrust()`. `LoadErrorPage.create` fills the load error page for a `LoadErrorKind` (insecure, dangerous, crashed, network, generic: the state of the page, which picks its glyph and buttons); each engine maps its errors to it (`GeckoLoadErrors`, `WebViewLoadErrors`). GeckoView gets the page as a base64 `data:` url from `onLoadError`. WebView has no way to restyle its own error page: `WebViewEx.onReceivedError` (main frame only, not for the certificate warning) keeps the page, and when WebView's error page finishes loading the page is written over it with `document.write` (`WebViewLoadErrors.replaceDocumentScript`), which adds no history entry; the script of the page is in a function (the globals of WebView's page stay) and sets `TVBRO_errorPage`, and when that is not set the page is loaded with `loadDataWithBaseURL` instead. Safe Browsing of WebView is always on (not tied to ad blocking); a hit of the main frame (`onSafeBrowsingHit`) is answered with `backToSafety`, so the load fails with `ERROR_UNSAFE_RESOURCE` and the page of a dangerous site shows the threat type. When the renderer of WebView dies (`onRenderProcessGone`, which returns true: false ends the app), each engine drops its view; the current tab tells the core (`TabEngineEvents.onEngineViewLost`), which attaches a new view, and the engine shows the crashed page for the lost url in it (Reload loads it again); a background tab gets a new view, restored from its saved state, when it is shown. GeckoView reopens a crashed session itself (`MyContentDelegate.onCrash`/`onKill`).

**Look.** Colors come from theme tokens: `?attr/tbColor…` attributes (`values/attrs.xml`) that `Theme.TVBro` maps to the semantic palette in `values/colors.xml` (night values in `values-night`). Layouts and drawables use the attributes, never hex colors or palette colors directly; code uses `Context.themeColor(R.attr…)`. Attributes need a themed (activity) context: do not inflate such views or drawables with the application context. A theme attribute does not resolve in `android:drawable` of a selector item (the drawable fails to load): put the color in a `<color>` or `<shape>` element inside the item. `ThemeResourcesTest` loads every drawable and color of the app with the app theme. The redesigned screens (the TV bar, the phone UI) use the tokens of the "TV Bro" design system instead: `?attr/tbColorDs…` attributes named as in its `tokens.json` (mapped to `ds_…` palette colors, night values in `values-night`; `tbColorDsDanger` is only for the glyphs of an insecure connection, never a fill), `ds_…` dimens, the `Widget.TVBro.Text.Address`/`Toast`/`MenuItem`/`TabTitle`/`CountBadge` styles and the `ds_…` state drawables (focused also when hovered by the cursor, selected when activated or selected). The other screens keep the older `tbColor…` palette until they are redesigned. Widgets get their look from styles in `values/styles.xml`, set with `style="..."` on each view: `Widget.TVBro.Button`/`Widget.TVBro.ImageButton` (the app button background; `.Ds.Segment`, `.Ds.Standalone` and `.Ds.Field` are the buttons of the redesigned bar, `.Ds.CursorMenu` the round buttons on the plate of the cursor menu) and `Widget.TVBro.Text.*` for text sizes (`Headline`, `Title`, `Subtitle`, `Body`, `Caption`, `Badge`; sizes in `values/dimens.xml`). These text styles set only `textSize`: a `textAppearance` would replace the default text color of the view. The theme sets no widget defaults (`buttonStyle` and others), so a view without a style keeps the platform look. Alert dialogs are the exception: `Theme.TVBro` sets `alertDialogTheme` to `ThemeOverlay.TVBro.Dialog.Alert` (the `ds_dialog_bg` window, ink text, `Widget.TVBro.DialogButton` buttons, `ds_menu_row_bg` list rows), so dialogs use `androidx.appcompat.app.AlertDialog` (in the gecko module too), never `android.app.AlertDialog` or `ProgressDialog`, which ignore it; `DialogThemeTest` checks the day and night looks. Repeated spacing values are dimens (`settings_content_padding`, `list_item_padding_*`). Icons are one vector per glyph with a role name (`ic_back`, `ic_close`, `ic_favorites`…): white paths and `android:tint="@color/icon_tint"`, which gives the icon color and the disabled one for a disabled view, so there are no per-color copies or selectors swapping images. A view that needs another color sets `app:tint` with a token (`tbColorIconSubtle` for the bookmark edit and delete buttons). An icon needed at another size in a `wrap_content` button gets a `layer-list` wrapper with the size, not a fixed view size: the button is then rounded to pixels like other icons of that size.

**Lists.** Lists are `RecyclerView`s with focusable rows (`Widget.TVBro.ListItem`: focusable, `list_item_bg_selector` background); there is no `ListView` left. The rows of the settings are the exception: they are a form (`SettingsRowsView`, see Settings), not a list. History and downloads are lists grouped by days (`widgets/datedlist`): `DatedListAdapter` (a `ListAdapter` that builds the header rows from the items, diffed in the background; act on the new rows in the `submitItems` callback), `StickyHeaderDecoration` (the pinned header of the top day with its shadow; items that are `isPinned` make a group of their own before the days, like the downloads in progress), `ListDividerDecoration` (its color and height can be given), and `StickyHeaderLayoutManager` (scrolls a focused row out from under the pinned header). They are in a `NearestFocusRecyclerView`: focus coming into the list from another view (`nextFocus...` set to the list) goes to the row nearest to that view, as in a ListView, and a focus request made while the layout is pending keeps the row that got it.

## Release

Releases use the manual `.github/workflows/release.yml` workflow (`workflow_dispatch` with a version). It builds per-ABI `genericGeckoIncluded` APKs (`-PenableAbiSplits`) and the `genericGeckoExcluded` release APK, renames them `tvbro-<version>-...apk`, and publishes a GitHub release whose body is `RELEASE_NOTES.md`. A version bump touches `versionCode`/`versionName` in `app/build.gradle.kts`, `latest_version.json`, `RELEASE_NOTES.md`, and the F-Droid/Play metadata changelog under `metadata/en-US/changelogs/<versionCode>.txt`. The app reads `latest_version.json` from `master` on GitHub, so changes to it go live once merged. In each channel, `url` is the `genericGeckoExcluded` APK, `minAPI` is 24 and there are no `urls` (an ABI match in them wins over `url`, so `genericGeckoIncluded` APKs there would be offered to the WebView app); `variants.geckoIncluded` holds `minAPI` 26 and the per-ABI `genericGeckoIncluded` APKs (`url`, `urls`); see Flavors.
